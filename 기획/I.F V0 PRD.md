# I.F V0 PRD

## 0. Critical Rules

다음 규칙은 I.F. V0 기획, 디자인, 개발, 운영 전 과정에서 반드시 지켜야 한다.

- 프로덕션 DB에 직접 쿼리 금지. 데이터 변경 또는 조회 테스트는 반드시 staging 또는 local 환경에서 먼저 검증한다.
- `.env`, `credentials.json`, API key, OAuth secret, 결제 secret, DB 접속 정보 등 시크릿 파일은 절대 커밋하지 않는다.
- `main` 브랜치에 직접 push 금지. 모든 변경은 별도 브랜치에서 작업하고 PR을 통해 검토 후 merge한다.
- V0는 웹 기반 MVP로 시작하되, 국내 패션 소비의 모바일 중심성을 고려해 모바일 웹 경험을 핵심 검증 범위에 포함한다.
- 향후 모바일 앱 전환 또는 React Native/Expo 기반 앱 확장이 가능하도록 API-first 구조와 프론트엔드/백엔드 분리를 전제로 설계한다.
- 로그인, 프롬프트 처리, AI 룩 생성, 상품 추천, 저장, 토큰 차감은 특정 웹 화면에 종속되지 않는 API 중심 기능으로 분리한다.
- Google/Kakao/Naver 인증은 향후 앱 확장을 고려해 OAuth callback, redirect URI, deep link 전략을 TRD에서 별도로 정의한다.
- 사용자의 프롬프트, 저장 룩, 공개/비공개 설정, 신체 관련 입력값은 개인정보 및 민감 정보 가능성을 고려해 최소 수집, 명시적 동의, 목적 제한 원칙을 따른다.
- 외부 쇼핑몰 구매 링크, 어필리에이트 링크, 추천 상품 노출은 사용자에게 오해가 없도록 표시 정책을 분리해 관리한다.
- V0 범위 밖 기능인 이미지 업로드, 얼굴 합성, 가상 피팅, 셀럽/인플루언서 이미지 기반 생성은 별도 정책과 법무 검토 전까지 구현하지 않는다.
- AI 룩 이미지는 한국 20-30대 여성 데일리 패션과 국내 온라인몰에서 실제 구매 가능한 착장 맥락을 기본값으로 한다.
- AI 룩 이미지는 상의/하의 또는 원피스/아우터 등 전체 착장 구성이 명확히 보여야 한다. 상반신만 보이거나 하의가 잘려 상품 매칭이 어려운 이미지는 실패 결과로 본다.
- 기본 생성 이미지는 한국 또는 동아시아권 모델, 국내 도시/일상 배경, 한국 패션 커머스 맥락에 가까운 무드를 우선한다.
- 사용자가 특수하거나 과감한 스타일을 입력하더라도, V0에서는 국내 상품으로 연결 가능한 wearable version으로 해석해 생성한다.
- 문서·작업 거버넌스 단일 지도는 `docs/DOC_MAP.md`. `docs/` ↔ 한국어 원본(`기획/`, `기술/`) sync는 pre-commit `sync-warn` 훅이 자동 경고하며, `main` 보호·시크릿 가드·TDD 가드·sync 경고 4종이 사고를 사전 차단한다. 비개발자 commander × AI 에이전트 협업 모델과 자동 가드 세부는 `docs/ADR.md` ADR-010, 문서 거버넌스 세부는 ADR-011 참조.

- I.F.의 장기 비전은 유지하되, V0에서는 핵심 사용자 경험 검증에 집중한다.

## 2. Product Summary

I.F.는 사용자가 텍스트 프롬프트로 상상한 패션 스타일을 AI 룩 이미지로 시각화하고, 그 룩과 유사하거나 어울리는 실제 구매 가능한 국내 패션 상품으로 연결해주는 AI 패션 탐색 서비스다.

브랜드 메시지:

> Wear what you imagine.

핵심 확장 문장:

> If you can imagine, you can wear it.

V0 제품 정의:

> I.F. V0는 20-30대 여성 사용자가 텍스트 프롬프트로 원하는 스타일을 입력하면, AI가 1-3개의 패션 룩 이미지를 생성하고, 각 룩에 어울리는 실제 구매 가능한 국내 패션 상품을 추천/연결하는 웹 기반 MVP다. 단, 국내 의류 소비의 모바일 중심성을 고려해 모바일 웹 경험을 핵심 검증 범위에 포함하고, 향후 모바일 앱 전환이 가능한 구조로 설계한다.

I.F.는 자사몰이 아니다. 직접 상품을 판매하거나 자체 결제를 처리하지 않는다. I.F.는 여러 온라인몰, 브랜드, 플랫폼에 흩어진 패션 상품을 사용자 의도에 맞게 연결하는 독립형 AI 탐색 레이어다.

## 3. Core Positioning

I.F.의 핵심 포지션:

- 사진 검색 서비스가 아니라 프롬프트 기반 패션 탐색 서비스
- 쇼핑몰이 아니라 여러 쇼핑몰/브랜드를 연결하는 AI 커머스 인터페이스
- 단순 AI 이미지 생성기가 아니라 실제 구매 가능한 상품까지 이어지는 패션 도구
- 범용 챗봇이 아니라 한국 여성 패션에 특화된 AI 스타일 디렉터

사용자에게 반복해서 전달할 문장:

> 상상한 스타일을 말하면, AI가 룩으로 보여주고 실제 살 수 있는 옷으로 연결합니다.

경쟁 서비스와의 차이:

- 지그재그 직잭렌즈: 사진 기반, 지그재그 내부 상품 검색 중심
- Zara AI Try-On: 자사 상품을 사용자에게 입혀보는 브랜드 내부 기능
- I.F.: 텍스트 프롬프트 기반, 여러 쇼핑몰/브랜드를 가로지르는 독립형 탐색

## 4. Target Users

### 4.1 Primary Target

20-30대 여성 패션 소비자

특징:

- 온라인 패션 쇼핑을 자주 한다.
- 인스타그램, 유튜브, 핀터레스트, 연예인/인플루언서 룩에서 패션 영감을 받는다.
- 무신사, 29CM, 지그재그, 에이블리, 네이버 쇼핑, 브랜드 자사몰을 오가며 쇼핑한다.
- 원하는 스타일은 있지만, 어떤 검색어로 찾아야 할지 모르는 경우가 많다.
- 너무 많은 상품과 쇼핑몰 때문에 탐색 피로를 느낀다.

### 4.2 Primary Use Cases

- "이런 스타일 옷은 어디서 찾지?"
- "온라인몰이 너무 많아서 보기 힘들다."
- "내가 생각하는 느낌대로 옷을 찾고 싶다."
- "좋아하는 유명인/인플루언서의 옷을 나도 비슷하게 입어보고 싶다."
- "상황, 계절, 분위기에 맞는 룩을 빠르게 보고 싶다."

## 5. Problem Statement

사용자는 패션 상품을 구매하기 전 다음 문제를 겪는다.

1. 원하는 스타일을 정확한 상품명이나 카테고리로 표현하기 어렵다.
2. 여러 쇼핑몰을 돌아다니며 비슷한 상품을 찾는 과정이 피곤하다.
3. 쇼핑몰 검색은 상품 중심이고, 사용자의 상상/상황/무드를 충분히 이해하지 못한다.
4. AI 이미지 생성 도구는 상상을 시각화할 수 있지만, 실제 구매 가능한 상품과 연결되지 않는다.
5. 사진 기반 검색은 이미 본 옷을 찾는 데는 유용하지만, 아직 머릿속에만 있는 스타일을 찾는 데는 한계가 있다.

I.F. V0는 이 중 1-4번 문제를 우선 해결한다.

## 6. Product Goals

### 6.1 V0 Goals

- 사용자가 텍스트 프롬프트로 패션 스타일을 입력할 수 있게 한다.
- AI가 사용자의 프롬프트를 패션 의도, 상황, 무드, 아이템 구성으로 해석한다.
- AI가 1-3개의 패션 룩 이미지를 생성한다.
- 각 AI 룩을 실제 구매 가능한 상품 조합과 연결한다.
- 사용자가 룩, 프롬프트, 상품 추천 결과를 저장할 수 있게 한다.
- 초기 상품 DB와 사용자 피드백을 통해 프롬프트-룩-상품 매칭 품질을 검증한다.

### 6.2 Non-Goals For V0

V0에서 하지 않는 것:

- 자체 결제
- 물류, 배송, 환불, CS
- 얼굴 기반 가상 피팅
- 사용자를 닮은 AI 모델 생성
- 셀럽 이름 기반 AI 이미지 생성
- 전체 쇼핑몰 자동 크롤링
- 완전한 실시간 재고/가격 동기화
- 공개 커뮤니티 피드의 완성형 구현
- 모바일 앱 출시

## 7. Product Scope

### 7.1 Platform

V0는 웹 기반 MVP로 출시한다. 다만 국내 패션 소비가 모바일 중심으로 이루어진다는 점을 고려해, V0부터 모바일 웹 경험을 핵심 검증 범위에 포함한다.

우선순위:

1. 모바일 웹 핵심 플로우
2. 데스크톱 웹 작업 공간
3. 향후 모바일 앱 전환 가능성

원칙:

- Web-first MVP, mobile-ready architecture
- V0는 웹으로 빠르게 검증하되, 앱 전환 가능성을 해치지 않는 구조로 설계한다.
- 로그인, 프롬프트 처리, 룩 생성, 상품 추천, 저장, 토큰 차감은 API 중심으로 분리한다.
- 웹 화면 안에 핵심 비즈니스 로직이 과도하게 묶이지 않도록 프론트엔드와 백엔드를 분리한다.
- 모바일에서는 상품 패널, 저장, 공유, 히스토리 접근이 앱 경험으로 자연스럽게 확장될 수 있어야 한다.
- 데스크톱에서는 더 넓은 화면을 활용해 탐색과 비교가 편한 작업 공간을 제공한다.
- 데스크톱과 모바일 모두에서 핵심 플로우가 깨지지 않도록 반응형으로 구성한다.

데스크톱 구조:

- 왼쪽: 사이드바
- 중앙: 프롬프트 입력, AI 룩 결과
- 오른쪽: 룩 클릭 시 상품 패널

모바일 구조:

- 상단: 로고, 메뉴, 토큰/계정 정보
- 중앙: 프롬프트 입력, AI 룩 결과 세로 스크롤
- 상품 패널: 하단 바텀시트
- 히스토리/저장: 메뉴 또는 별도 탭

### 7.2 Initial Category Scope

V0의 상품 범위:

- 여성 의류
- 20-30대 여성 패션
- 전체 룩 기준 500개 curated look DB

포함:

- 상의
- 하의
- 원피스
- 아우터

제외:

- 신발
- 가방
- 액세서리
- 속옷
- 수영복
- 화장품

## 8. Core User Flow

### 8.1 Landing Flow

1. 사용자가 I.F. 웹사이트에 진입한다.
2. 첫 화면에서 브랜드 영상 배경과 메시지를 본다.
3. 사용자는 `Get Started`를 클릭한다.
4. **Explore 진입 피드**가 표시된다 — 큐레이션 룩 6-12개 + 시즌 데모 프롬프트 3-5개. 빈 프롬프트 입력창은 보여주지 않는다.
5. 사용자는 Explore에서 룩 카드를 클릭하거나, 데모 프롬프트를 선택하거나, 직접 프롬프트를 입력한다.
6. 룩 카드/데모 프롬프트 클릭 시 그 프롬프트가 자동 입력된 워크스페이스로 진입한다.
7. 비로그인 사용자가 Generate/Save를 트리거하면 로그인 화면으로 유도된다.
8. 사용자는 Google, Naver, Kakao 중 하나로 로그인한다.
9. 로그인 후 데모 프롬프트 1회를 실행하거나 직접 프롬프트를 입력한다.

### 8.2 Prompt To Look Flow

1. 사용자가 프롬프트 입력창에 원하는 스타일을 입력한다.
2. 필요 시 추천 질문/필터가 사용자를 보조한다.
3. 사용자가 키, 몸무게, 선호 핏, 피부톤, 예산 등을 입력하거나 생략한다.
4. AI가 프롬프트를 해석한다.
5. AI가 1-3개의 패션 룩 이미지를 생성한다.
6. 사용자는 생성된 룩 중 하나를 클릭한다.
7. 우측 상품 패널이 열린다.
8. 패널에는 전체 룩의 메인 추천 상품 조합과 유사 상품이 표시된다.
9. 사용자는 상품 링크를 클릭해 외부 쇼핑몰로 이동한다.
10. 사용자는 룩/프롬프트/상품 결과를 저장하거나 공유한다.

### 8.3 Follow-Up Prompt Flow

사용자는 생성된 룩에 대해 후속 프롬프트를 입력할 수 있다.

예:

- "치마만 빨간색 제품으로 바꿔줘."
- "좀 더 출근룩처럼 바꿔줘."
- "가격대를 낮춰줘."
- "하체 커버되게 바꿔줘."
- "상의는 유지하고 하의만 바꿔줘."
- "조금 더 미니멀하게 바꿔줘."

후속 프롬프트 결과:

- 기존 룩을 기준으로 수정된 룩이 생성된다.
- 변경된 의도에 맞는 상품 조합이 다시 추천된다.
- 기존 결과와 새 결과는 히스토리에 남는다.

### 8.4 Mini-Action Pattern (ADR-009 참조)

V0는 풀 멀티턴 채팅 UI를 도입하지 않는다. 대신 싱글샷 워크스페이스 위에 다음 3개 mini-action을 제공해 "AI와 좁혀가는 대화 가치"의 약 80%를 흡수한다.

- **#1 다시 생성** — 결과 카드 위 버튼. 같은 의도로 다른 룩 1-3개 재생성.
- **#2 조건 좁히기 (정제 칩)** — "더 캐주얼하게"·"색 변경"·"가격대 ↓" 등 보조 칩. 칩 클릭은 silent filter가 아니라 **새 conversation turn으로 처리**된다. AI가 기존 의도에 칩 조건을 보정해 재검색·생성.
- **#3 More Like This** — 각 룩/상품 카드 우측 하단 버튼. 그 룩 기반으로 변주 3개 생성(스타일·색·핏 변형). 사용자 트리거 방식.

풀 채팅 UI 도입은 V1에서 사용자 피드백 데이터를 보고 재검토한다.

### 9.8 Non-Auth State Variants

비로그인 사용자가 Save·History·Generate 등 인증 필요 액션을 트리거할 때의 UX 규칙:

- **Save 버튼**: 비로그인 상태에서 사전 표기 — 버튼 옆에 "로그인하고 저장" 텍스트 또는 자물쇠 아이콘. 클릭 시 로그인 모달.
- **History 화면**: 비로그인 시 빈 리스트 X. "내 룩 컬렉션을 만들려면 로그인" 메시지 + 가입 CTA + sample 룩 미리보기 3-6개.
- **Generate**: 비로그인 상태에서 프롬프트 입력은 허용. Generate 클릭 시 로그인 모달.

Daydream은 Save 클릭 후 가입 모달을 띄워 "저장됐다"는 기대를 깨뜨린다. I.F.는 사전 표기로 이를 회피한다.

## 10. Functional Requirements

### 10.1 Prompt Input

사용자는 자유 텍스트로 프롬프트를 입력할 수 있어야 한다.

프롬프트 예시:

- "여름 데이트에 입을 꾸안꾸 룩"
- "키 162cm, 하체 커버되는 출근룩"
- "제니 사복처럼 미니멀한 블랙 데일리룩이지만 부담스럽지 않게"
- "한강 피크닉에 어울리는 사진 잘 나오는 룩"

지원해야 할 입력 정보:

- 상황
- 계절
- 장소
- 무드
- 예산
- 키
- 몸무게
- 선호 핏
- 피부톤
- 선호/비선호 스타일

### 10.2 Prompt Builder

사용자가 빈 입력창 앞에서 막히지 않도록 추천 질문과 선택형 보조 입력을 제공한다.

필터 예시:

- 상황: 데이트, 출근, 여행, 하객룩, 일상, 카페, 피크닉
- 계절: 봄, 여름, 가을, 겨울
- 무드: 캐주얼, 미니멀, 러블리, 스트릿, 시크, 페미닌
- 예산: 5만원 이하, 10만원 이하, 20만원 이하, 제한 없음
- 핏: 슬림핏, 세미오버핏, 오버핏, 하체 커버, 허리 강조

### 10.3 Demo Prompt

로그인한 사용자는 데모 프롬프트를 1회 실행할 수 있다.

데모 프롬프트는 계절, 검색량, 트렌드 데이터를 참고해 주기적으로 변경한다.

예:

- 4월: 벚꽃 데이트룩, 봄 하객룩
- 6월: 여름 데이트룩, 장마철 출근룩
- 9월: 가을 캠퍼스룩, 환절기 데일리룩
- 12월: 연말 모임룩, 겨울 데이트룩

데모 프롬프트 목적:

- 사용자가 I.F.의 핵심 경험을 이해하게 한다.
- 실제 생성 비용을 통제한다.
- 계절/트렌드 기반 패션 해석 능력을 보여준다.

### 10.4 AI Look Generation

V0의 핵심 결과물은 AI가 생성한 1-3개의 패션 룩 이미지다.

생성 방식:

- 하이브리드 방식
- 데모/인기 프롬프트는 사전 생성/검수된 고품질 결과를 사용할 수 있다.
- 로그인 사용자의 자유 프롬프트는 신규 AI 룩을 생성한다.
- 유사한 프롬프트가 있을 경우 기존 공개/검수된 룩을 참고할 수 있다.

생성 결과:

- 최소 1개, 최대 3개 룩
- 각 룩은 서로 다른 스타일 해석 가능
- 결과는 프롬프트와 함께 저장 가능

품질 기준:

- 의류가 명확히 보일 것
- 상의/하의 또는 원피스/아우터 등 전체 룩 구성이 상품 매칭 가능할 정도로 보일 것
- 프롬프트의 계절/상황/무드가 반영될 것
- 한국 20-30대 여성 데일리 패션 맥락에 맞을 것
- 기본 생성 결과는 한국 또는 동아시아권 모델과 국내 일상 배경의 무드를 우선할 것
- 너무 비현실적이거나 국내 상품 구매 연결이 어려운 의상은 지양할 것
- 런웨이, 코스튬, 판타지, 무대의상처럼 V0 상품 매칭이 어려운 결과는 사용자가 명시적으로 요청하더라도 wearable version으로 완화할 것
- 실제 상품 매칭이 가능한 수준의 아이템 구조를 가질 것

### 10.5 Curated Look DB

V0는 전체 룩 기준 500개 curated look DB로 시작한다.

목적:

- 전체 쇼핑몰 자동 연동 전, 제한된 상품 데이터로 핵심 경험을 검증한다.
- 프롬프트 → AI 룩 → 실제 상품 추천 플로우가 작동하는지 확인한다.
- 데이터 품질을 직접 통제한다.

룩 데이터 구성:

- 룩 이름
- 대표 프롬프트
- 생성 이미지
- 시즌
- 상황
- 무드
- 색상
- 핏
- 타겟 연령
- 구성 아이템
- 상품 링크
- 유사 상품 링크
- 관련 상품 링크
- 공개/비공개 활용 가능 여부

룩 예시:

```text
Look 001
- Prompt: 여름 데이트에 입기 좋은 꾸안꾸 룩
- Season: summer
- Mood: casual, clean, lovely
- Items:
  - Top: 린넨 셔츠
  - Bottom: 세미와이드 데님
  - Outer: 없음
- Main product links
- Similar product links
- Generated image
- Tags
```

### 10.10 Mini-Actions

V0의 결과 화면은 풀 멀티턴 채팅이 아니라 mini-action 3개로 후속 정제를 제공한다. (ADR-009 참조)

#### #1 다시 생성

- 위치: 각 결과 룩 카드 위
- 동작: 같은 의도로 새 룩 1-3개 재생성
- 비용: 토큰 1회 소모 (free tier는 데모 프롬프트 외 일정 횟수 제한)

#### #2 조건 좁히기 (정제 칩)

- 위치: 결과 화면 상단 또는 입력바 위
- 칩 종류 (예시): "더 캐주얼하게", "더 미니멀하게", "색 변경", "가격대 ↓", "하체 커버", "오버핏"
- 동작: 칩 클릭은 silent filter가 아니라 **새 conversation turn으로 처리**된다.
  - AI가 기존 프롬프트 + 칩 조건을 결합해 의도 재해석
  - 새 룩/상품 결과 생성
  - 히스토리에 새 turn으로 기록
- 칩은 결과 맥락에 따라 동적으로 변경될 수 있다 (예: 가격대 칩은 가격 필드가 있는 결과에만)

#### #3 More Like This

- 위치: 각 룩 카드 + 각 상품 카드 우측 하단
- 라벨 후보: "이런 스타일 더", "비슷한 룩 보기"
- 동작: 그 룩/상품 1개를 기준으로 변주 3개 생성 (스타일·색·핏 변형 중 하나)
- Daydream 분석에서 "가장 강한 기능"으로 평가된 패턴 — 사용자의 취향 피벗을 빠르게 만든다

#### 풀 채팅 UI 미도입 사유

- 인지 부담 증가 (사용자가 무한 대화에 지침)
- 토큰 비용 증가 (대화 컨텍스트 누적)
- "Editorial AI Studio" 컨셉과 불일치
- V0 범위·일정 초과

V1에서 사용자 피드백 데이터를 본 뒤 재검토. 현재 mini-action 3개로 "대화 가치"의 약 80%를 흡수.

## 11. Monetization Requirements

V0는 월구독 + 토큰 모델을 전제로 설계한다. **토큰 단위·차감 매트릭스·결제 모델 세부는 `docs/ADR.md` ADR-012가 single source of truth.** 본 섹션은 정책의 사용자 경험·범위 결정을 담고, 가격·토큰량 등 운영 수치는 ADR-012에서 박힌 값을 따른다.

핵심 단위 정의: **1회 검색 = 10토큰 = 룩 3개**. 모든 generation 액션(자유 프롬프트 / 다시 생성 / 정제 칩 / More Like This / demo seed)이 동일 10토큰 차감. save·view·share는 무과금.

### 11.1 Free Tier (V0 Core)

가능 기능:

- 랜딩 페이지 탐색
- 서비스 소개 영상 확인
- 로그인 후 제한된 데모 프롬프트 체험
- **가입 시 1회 10토큰 그랜트 (= 1회 검색)** — 갱신 없음, 체험판 성격
- 저장 룩 5개 누적 슬롯

제한 기능:

- 이미지 업로드 검색
- 인플루언서/연예인 옷 유사 상품 검색
- 내 얼굴 합성
- 고급 개인화
- 무제한 저장

### 11.2 Paid Tier (V0 Extended — Pro / Max 2-tier)

**Pro 9,900원/월** (한국 SaaS 황금 포인트):

- 월 100토큰 (= 10회 검색)
- 매월 1일 자동 충전, 익월 expire (이월 없음)
- 저장 룩 5개 누적 슬롯
- 고급 필터·공개/비공개 룩 관리 확장

**Max 19,900원/월** (헤비 사용자):

- 월 200토큰 (= 20회 검색)
- 매월 1일 자동 충전, 익월 expire
- 저장 룩 **무제한**
- Pro의 모든 기능 + 무제한 saved + advanced 기능 플래그

**별도 토큰 충전(topup)은 V0.5+ 후순위 검토.** 결제·환불·세금계산서 운영 부담 최소화를 위해 V0/V0 Extended에선 Pro/Max 구독으로만 흡수.

### 11.3 Future Paid Features

추후 유료 기능:

- 인플루언서/연예인 사진 기반 유사 상품 검색
- 내가 가진 옷 사진 기반 스타일 제안

## 13. AI Requirements

### 13.1 Prompt Interpretation

AI는 사용자의 프롬프트를 다음 요소로 분해해야 한다.

- 성별
- 연령대
- 계절
- 상황
- 장소
- 무드
- 아이템 구성
- 색상
- 핏
- 예산
- 체형/선호 조건

예:

"여름철 남친룩"

→ 계절: 여름  
→ 무드: 깔끔함, 데일리, 호감형  
→ 아이템 후보: 린넨 셔츠, 반팔 니트, 와이드 슬랙스  
→ 색상 후보: 화이트, 스카이블루, 네이비, 베이지  

### 13.2 Trend-Informed Prompt Mapping

모호한 프롬프트는 외부 검색/콘텐츠 트렌드와 내부 스타일 taxonomy를 참고해 해석한다.

V0 적용 방식:

- 데모 프롬프트와 주요 시즌 프롬프트부터 수동/반자동으로 관리
- "꾸안꾸", "하객룩", "출근룩", "남친룩" 같은 한국어 패션 표현을 사전으로 구축
- 장기적으로 검색량/저장/클릭 데이터를 반영해 업데이트

### 13.3 Look Generation

AI 룩 이미지는 프롬프트 기반으로 생성한다.

요구사항:

- 모델과 배경이 룩의 상황을 표현해야 한다.
- 의류 아이템이 명확해야 한다.
- 상의/하의 또는 원피스/아우터 등 전체 착장 구성이 확인 가능해야 한다.
- 한국 데일리 패션과 국내 상품 매칭 가능성을 기본 품질 기준으로 둔다.
- 기본 생성 맥락은 한국 또는 동아시아권 모델, 서울/국내 일상 배경, 국내 패션 커머스 무드를 우선한다.
- V0에서는 얼굴 유사성보다 스타일/착장 표현을 우선한다.
- 생성 이미지가 실제 상품 추천과 연결 가능해야 한다.

### 13.4 Product Matching

AI 룩과 curated look DB/상품 DB를 연결한다.

V0에서는 완전 자동 매칭보다, curated look DB 기반 매칭을 우선한다.

매칭 기준:

- 카테고리
- 색상
- 핏
- 무드
- 상황
- 계절
- 가격대
- 아이템 구성

## 17. Risks And Mitigations

### 17.1 AI Image Quality Risk

위험:

- AI 룩 이미지가 어색하거나 실제 상품과 매칭하기 어려울 수 있다.

대응:

- 데모/인기 프롬프트는 사전 생성/검수 결과 사용
- 생성 룩은 1개가 아니라 최대 3개 제공
- 너무 비현실적인 결과는 재생성/수정 가능하게 함

### 17.2 Product Matching Risk

위험:

- 추천 상품이 AI 룩과 충분히 비슷하지 않을 수 있다.

대응:

- V0는 curated look DB 500개로 시작
- 룩 단위로 상품 조합을 사전 검수
- 사용자 피드백 수집

### 17.3 Scope Creep Risk

위험:

- 이미지 업로드, 가상 피팅, 커뮤니티, 자체 결제까지 한 번에 만들려 할 수 있다.

대응:

- V0는 텍스트 프롬프트 기반 AI 룩 생성과 상품 연결에 집중
- 확장 기능은 별도 버전으로 분리

### 17.4 Legal Risk

위험:

- 인플루언서/연예인 이미지, 얼굴 합성, 사용자 업로드 이미지가 법적 이슈를 만들 수 있다.

대응:

- V0에서는 이미지 업로드 기능 제외
- 셀럽 이름 기반 이미지 생성 금지
- 향후 이미지 업로드 기능 출시 전 별도 약관/정책 수립

### 19.1 백엔드 안전 보강 결정 (ADR-013~017)

V0 출시 전 발견한 백엔드 V0-critical 구멍 6개에 대한 결정. 세부 스펙·SQL·엔드포인트 계약은 `docs/ADR.md`와 `docs/BACKEND_HARDENING_V0.md`가 single source of truth이며, 본 절은 PRD 레벨 요약이다. 모든 결정은 ADR-012의 토큰 양/개수(1회 검색=10토큰=룩 3개, 항상 3개, `max_looks` 미노출)와 ADR-003의 단가·마진 수치를 **건드리지 않고** 차감 "방식"과 운영 안전성만 보강한다.

- **ADR-013 (AI 생성 실행 모델)**: `/api/looks/generate`를 Node.js runtime + maxDuration 상향(60초 목표, Vercel 플랜 한도 내) **동기** 처리로 시작하고, 룩 3장은 `Promise.all` 병렬 생성으로 지연을 단축한다. 정석은 비동기 작업큐지만 V0 Tier 2 볼륨(월 약 3,000 이미지)엔 큐/워커 인프라가 과해 동기 + maxDuration이 가장 단순. 재검토 트리거: p95 지연이 함수 한도의 70% 도달 또는 동시 생성 급증. (열린 항목 → 해결 2026-06-04: Vercel Hobby(무료)가 maxDuration 60초 허용(+Fluid Compute 300초) → V0는 무료 Hobby 출시, Vercel Pro 불필요.)
- **ADR-014 (토큰 차감 정합성)**: 단일 Postgres RPC `consume_tokens()`(행 잠금 → 잔액 확인 → 거래 기록 → 잔액 갱신을 한 트랜잭션), `CHECK(token_balance >= 0)` 제약, `X-Idempotency-Key` 헤더 기반 멱등성 키(`token_transactions.idempotency_key` + `unique(user_id, idempotency_key)`), 생성 실패/3장 미달 시 자동 환불(`refund_tokens()`, 3장 all-or-nothing)을 도입한다. 동시 요청·더블클릭의 이중 차감·음수 잔액을 분산락 없이 Supabase 단독으로 막는다. ADR-012의 10토큰 일률·"항상 3개"는 불변, 차감 "방식"만 안전화.
- **ADR-015 (AI 비용 안전장치)**: OpenAI 대시보드 billing hard limit + email alert(무료, PO 수작업; Settings→Limits 월 예산 hard cap 초기값 월 $200·알림 50/80%, 2026-06-04 PO 결정), 전역 일일 spend cap(당일 누적 생성 호출 수를 `generation_history`에서 카운트해 초과 시 503 안내), 수동 kill switch를 둔다. 설정값(일일 상한·kill switch on/off)은 **env 환경변수**에 두어 새 테이블 추가 없이 10테이블 freeze를 유지한다. per-user 토큰 한도는 한 사용자만 막으므로 버그·악의로 인한 전체 호출 폭주 방지용 전역 상한이 필요. ADR-003 단가·ADR-012 마진은 불변, runaway 상한만 추가.
- **ADR-016 (보안 경계)**: `006_rls_policies.sql`에 전 테이블 RLS enable(읽기는 본인/공개만, 쓰기는 전부 service_role), 어드민 role(`app_metadata.role=admin` JWT + `users.role` 컬럼 + `/api/admin/*` 가드), 가입 grant 멱등(`INSERT ... ON CONFLICT DO NOTHING`로 1회만 10토큰), 기본 rate limit 초기값(유저 10회/분·IP 30회/분·가입 IP 5개/일)을 둔다. 정석은 별도 인증 서비스/WAF지만 Supabase RLS + 라우트 레벨 rate limit로 V0 충분. 무료 토큰 파밍 방지 포함.
- **ADR-017 (이미지 모델 build-vs-buy)**: V0는 OpenAI GPT Image 2(ADR-003) API 사용(**buy**)을 유지하고, 자체 패션 전용 이미지 모델 학습/파인튜닝은 V0 범위 밖 V1+ 후보로 둔다. 자체 학습은 비현실적(수백만 $·GPU·ML 팀)이고 저볼륨에선 API가 자체 GPU 호스팅보다 싸며, 해자(moat)는 모델이 아니라 데이터(상품 태그·캡션·역프롬프트·멀티모달 임베딩·피드백)다. 정석 논의는 "자체 모델=차별화"지만 V0 케이스는 속도·비용·해자 측면에서 buy가 정답. 재검토 트리거: 비용 손익분기 초과·파인튜닝 품질 개선 입증·벤더 리스크(DALL-E 3 API 종료가 증거).

DB·계약 측면 주요 변경: `users`에 `CHECK(token_balance >= 0)`·`role` 컬럼, `token_transactions`에 `idempotency_key` + `unique(user_id, idempotency_key)`, 신규 `006_rls_policies.sql`·`007_token_rpc.sql`(consume/refund RPC), `looks.generated_image_url`은 OpenAI URL이 아니라 Supabase Storage 경로/서명 URL로 영속화(OpenAI URL 24h 만료 대응), B-path 매칭 임계값 초기값 0.70. 새 테이블은 추가하지 않는다(10테이블 freeze 유지). 전체 추적표는 `docs/BACKEND_HARDENING_V0.md`(영문 단독 설계 추적 문서).

## 20. V0 Acceptance Criteria

V0가 성공적으로 구현되었다고 판단하는 기준:

- 비로그인 사용자는 Explore 진입 피드에서 큐레이션 룩과 시즌 데모 프롬프트를 볼 수 있다.
- 사용자는 로그인할 수 있다.
- 사용자는 Explore 카드를 클릭하거나 직접 프롬프트를 입력할 수 있다.
- 사용자는 정제 칩 클릭으로 새 conversation turn을 트리거할 수 있다 (silent filter 아님).
- 사용자는 AI 룩 이미지 1-3개를 받을 수 있다. 로딩 중 진행 텍스트가 표시된다.
- 사용자는 룩을 클릭해 상품 패널을 열 수 있다.
- 상품 패널에는 전체 룩 기준 메인 추천과 개별 아이템 상품이 표시된다.
- 사용자는 각 룩/상품 카드의 More Like This 버튼으로 변주 3개를 받을 수 있다.
- 사용자는 결과 카드의 "다시 생성" 버튼으로 새 룩을 받을 수 있다.
- 사용자는 외부 구매 링크를 클릭할 수 있다.
- 사용자는 결과를 저장할 수 있다. 비로그인 시 Save 버튼은 "로그인하고 저장" 사전 표기로 클릭 후 기대 깨지지 않는다.
- 저장 결과는 비공개/공개를 선택할 수 있다.
- 사용자는 저장한 룩을 다시 볼 수 있다. 비로그인 시 History는 가입 유도 화면이 표시된다.
- 운영자는 최소 500개의 curated look DB를 관리할 수 있다.
