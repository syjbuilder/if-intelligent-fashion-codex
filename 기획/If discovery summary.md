# I.F. Discovery Summary

## 1. Service Overview

I.F.는 "I am Fashion", "IF(가능성)", "Intelligent Fashion"이라는 세 가지 의미를 담은 AI 패션 플랫폼이다.

핵심 메시지는 다음 문장에 가깝다.

> Wear what you imagine.

핵심 확장 문장은 다음과 같다.

> If you can imagine, you can wear it.

I.F.는 사용자가 옷을 찾아다니는 방식에서 벗어나, 자신이 상상한 스타일을 AI와 함께 시각화하고 실제 구매 가능한 상품으로 연결하도록 돕는 서비스다.

서비스의 본질은 단순한 AI 코디 추천이나 쇼핑 검색이 아니라, "상상 → 시각화 → 실제 상품 연결 → 구매"로 이어지는 새로운 패션 커머스 인터페이스다.

## 2. Core Problem

현재 패션 소비자는 너무 많은 의류 브랜드, 쇼핑몰, 상품, 트렌드 속에서 원하는 옷을 찾는 데 많은 시간을 쓴다.

대표적인 문제는 다음과 같다.

- 머릿속에는 원하는 스타일이 있지만, 정확한 검색어로 표현하기 어렵다.
- 쇼핑몰에는 상품이 너무 많아 탐색 피로가 크다.
- 특정 상황, 계절, 장소, 분위기에 맞는 옷을 고르기 어렵다.
- SNS, 연예인, 인플루언서, 길거리 스냅에서 본 옷이 예뻐도 어디서 사는지 알기 어렵다.
- 내가 상상한 스타일과 실제 구매 가능한 상품 사이의 연결이 약하다.

I.F.는 이 문제를 AI 기반 대화형 인터페이스와 패션 이미지 생성, 상품 매칭 기술로 해결한다.

## 3. Product Direction

I.F.의 메인 입력 방식은 텍스트 프롬프트다.

사용자는 ChatGPT나 Claude에 말하듯이 원하는 옷, 상황, 분위기, 장소, 계절, 예산, 체형 힌트 등을 입력한다.

예시:

- "봄 데이트에 입을 캐주얼한 요가복 느낌"
- "파란 볼캡, 맨투맨, 청바지, 흰 운동화로 꾸민 듯 안 꾸민 듯한 코디"
- "키 160cm, 하체가 있는 편인데 첫 출근에 입기 좋은 옷"
- "한강 피크닉에 어울리는 편하지만 사진 잘 나오는 룩"

I.F.는 입력을 바탕으로 AI 패션 이미지 또는 룩 제안을 생성하고, 그 스타일과 유사한 실제 판매 상품을 연결한다.

이미지 업로드 기능은 초기 메인 기능이 아니라, 결제 단계 또는 유료 플랜에서 확장되는 추가 기능으로 본다.

이미지 업로드 기능의 목적은 셀럽 이름 기반 생성이 아니다. 사용자가 일상에서 본 연예인, 인플루언서, SNS 사진, 길거리 스냅 등을 업로드하면 사진 속 옷을 분석해 동일하거나 유사한 제품을 찾아주는 것이다.

즉, "장원영 스타일로 생성해줘"가 아니라 "이 사진 속 옷 어디서 살 수 있어?"에 가까운 기능이다.

이 점에서 I.F.는 지그재그의 직잭렌즈 같은 이미지 기반 유사 상품 검색 기능을 중요한 레퍼런스로 본다. 다만 I.F.의 출발점은 사진 검색이 아니라 텍스트 프롬프트다. 사용자가 먼저 "내가 상상하는 옷"을 말하고, AI가 그 상상을 패션 이미지와 실제 상품으로 번역하는 것이 메인 경험이다.

따라서 I.F.의 구조는 다음과 같이 구분한다.

- 메인 경험: 텍스트 프롬프트 → AI 패션 이미지/룩 생성 → 여러 쇼핑몰/브랜드 상품 연결
- 확장 경험: 사진 업로드 → 사진 속 의류 분석 → 동일/유사 상품 연결

이 구분은 향후 PRD에서 기능 우선순위, 무료/유료 정책, 경쟁 포지셔닝을 정할 때 중요한 기준이 된다.

## 4. Brand Philosophy

I.F.는 사용자의 상상력을 옷으로 실현하는 도구다.

동시에 I.F.는 모방과 창작의 관계를 인정한다. 사용자가 연예인, 인플루언서, 친구, 거리의 사람, SNS 이미지에서 영감을 얻는 것은 자연스러운 패션 탐색 방식이다.

I.F.의 관점은 다음과 같다.

> 상상력과 창작은 완전히 무에서 시작되지 않는다. 우리는 이미 본 것, 좋아한 것, 따라 해보고 싶은 것들을 바탕으로 더 풍부하게 상상한다.

따라서 이미지 업로드 기반 유사 상품 검색은 I.F.의 철학과 충돌하지 않는다. 오히려 사용자의 상상을 더 풍부하게 만드는 참고 자료이자 출발점이다.

## 5. Initial Target

초기 타겟은 국내 여성 패션 시장이다.

핵심 사용자는 다음과 같이 가정한다.

- 20-30대 여성
- SNS, 인플루언서, 연예인 룩, 트렌드에 민감한 사용자
- 무신사, 29CM, 지그재그, 에이블리, 브랜드 자사몰 등에서 자주 쇼핑하는 사용자
- 상황별/장소별/계절별 착장 고민이 많은 사용자
- "오늘 뭐 입지?", "이런 느낌의 옷 어디 없나?", "저 옷 비슷한 거 사고 싶다"는 문제를 자주 겪는 사용자

초기에는 여성 패션 안에서도 너무 넓게 시작하지 않고, 상황 기반 룩 탐색과 국내 브랜드 상품 연결에 집중한다.

## 6. V0 Scope

V0의 중심은 텍스트 프롬프트 기반 AI 패션 탐색이다.

V0에서 집중할 기능:

- 텍스트 프롬프트 입력
- 상황/장소/계절/분위기/예산/체형 힌트 입력
- AI 패션 이미지 또는 룩 무드 생성
- 생성된 룩을 구성하는 아이템 분해
- 국내 브랜드 자사몰 또는 주요 패션 커머스 상품과 유사도 매칭
- 실제 구매 가능한 상품 링크 제공

V0에서 제외하거나 약하게 다룰 기능:

- 사용자를 닮은 AI 모델 생성
- 얼굴 기반 가상 피팅
- 셀럽 이름 기반 이미지 생성
- 대규모 브랜드 직접 제휴
- 완전한 실시간 재고/가격 동기화

이미지 업로드 기반 "저 옷 어디서 사지?" 기능은 결제 단계 또는 유료 기능으로 확장 가능하다.

## 7. AI Model And Body Input Strategy

초기에는 "나를 닮은 AI 모델" 기능을 V0 핵심에서 제외한다.

대신 키, 체형, 선호 핏, 피부톤, 가리고 싶은 부위, 강조하고 싶은 분위기 등을 입력받아 AI가 스타일 추천과 이미지 생성에 반영하는 방식이 현실적이다.

기술적으로는 다음 단계로 나눌 수 있다.

1. 텍스트 기반 개인화
   - 사용자가 키, 체형, 선호 스타일을 입력한다.
   - AI가 이를 프롬프트와 추천 로직에 반영한다.
   - 예: "160cm", "하체가 있는 편", "짧은 상의 부담", "다리가 길어 보이는 핏 선호"
   - 기술 난이도는 낮은 편이다.

2. 일반 AI 모델의 체형 조정
   - 실제 사용자의 얼굴을 닮게 만들지는 않는다.
   - 대신 "160cm petite body", "curvy lower body", "straight body type"처럼 일반 모델의 체형을 조정한다.
   - 이미지 생성 모델이 체형을 완벽히 일관되게 유지하지는 못할 수 있지만, 얼굴 기반 VTON보다 난이도와 법적 리스크가 낮다.

3. 사용자 닮은 모델 또는 얼굴 기반 피팅
   - 장기 비전으로 남긴다.
   - 얼굴 이미지, 신체 이미지, 생체정보, 개인정보 동의, 저장/삭제 정책, 모델 품질 관리가 모두 필요하다.
   - V0에서 하기에는 기술적/법적/UX 리스크가 크다.

따라서 I.F.의 초기 개인화 전략은 "사용자를 닮게 만드는 것"보다 "사용자의 조건을 스타일 추천에 반영하는 것"이 적절하다.

## 8. Catalog Strategy

초기 상품 연결은 국내에서 규모가 큰 브랜드 자사몰과 주요 패션 커머스 상품을 우선으로 한다.

초기 전략은 다음과 같다.

- 국내 여성 패션 브랜드 자사몰을 우선 수집/연결한다.
- 이후 무신사, 29CM, 지그재그, 에이블리, 쿠팡, 어필리에이트 네트워크 등으로 확장한다.
- 초기에는 수십만 개 전체 상품보다, 특정 카테고리와 상황에 맞는 제한된 상품군으로 시작한다.
- 상품 데이터의 품질이 서비스 품질을 좌우하므로, 상품명, 이미지, 가격, 브랜드, 색상, 카테고리, 소재, 핏, 스타일 태그를 최대한 구조화한다.

장기적으로 I.F.의 해자는 AI 이미지 생성 자체보다 "국내 패션 상품 데이터와 사용자 프롬프트를 얼마나 잘 연결하는가"에서 생긴다.

지그재그, 무신사, 에이블리 같은 플랫폼은 각자의 앱 안에서 강력한 검색과 추천을 제공할 수 있다. 그러나 그들은 기본적으로 자사 플랫폼 안의 상품을 우선한다.

I.F.의 차별화는 하나의 앱이나 쇼핑몰에 갇히지 않고, 여러 브랜드 자사몰과 패션 플랫폼을 가로질러 사용자가 원하는 스타일에 가장 가까운 선택지를 찾아주는 데 있다.

즉, I.F.는 특정 쇼핑몰의 검색 기능이 아니라 "패션 상품 발견을 위한 독립적인 AI 탐색 레이어"를 지향한다.

## 9. Prompt-Based Generation Accuracy

I.F.에서 중요한 기술 과제는 사용자의 텍스트 프롬프트를 정확한 패션 이미지와 실제 상품 매칭으로 연결하는 것이다.

이 영역의 핵심 원칙은 다음과 같다.

> 초기에는 모델 파인튜닝보다 상품 데이터 구조화와 프롬프트-상품 매칭 데이터 자산 구축이 먼저다.

I.F.가 장기적으로 강해지려면 단순히 좋은 이미지 생성 모델을 호출하는 것에 그치면 안 된다. 실제 판매 상품을 AI가 이해할 수 있는 언어로 바꾸고, 사용자의 자연어 프롬프트와 상품 이미지/상품 속성/구매 가능한 링크를 연결하는 자체 데이터 구조가 필요하다.

따라서 향후 PRD와 개발 문서에는 "AI 모델 학습"보다 먼저 "상품 데이터 정제, 캡셔닝, 태깅, 역프롬프트 추출, 매칭 평가"가 핵심 요구사항으로 반영되어야 한다.

정확도를 높이기 위해 할 수 있는 작업은 다음과 같다.

### 9.1 상품 데이터 구조화

실제 판매 상품을 단순 이미지와 상품명으로만 보지 않고, 패션 속성 단위로 분해해야 한다.

예시 속성:

- 카테고리: 상의, 하의, 원피스, 아우터, 신발, 가방
- 세부 카테고리: 맨투맨, 크롭 티셔츠, 와이드 데님, 플레어 스커트
- 색상: 네이비, 아이보리, 라이트 블루
- 핏: 오버핏, 슬림핏, 하이웨이스트, 세미와이드
- 소재: 코튼, 나일론, 데님, 니트
- 무드: 캐주얼, 러블리, 미니멀, 스트릿, 발레코어, 올드머니
- 상황: 데이트, 출근, 여행, 운동, 하객룩
- 계절: 봄, 여름, 가을, 겨울

이 구조화된 태그가 있어야 프롬프트와 상품 사이의 의미적 연결이 좋아진다.

PRD 반영 항목:

- 상품 단위로 필수 메타데이터 스키마를 정의한다.
- 상품명, 브랜드, 가격, URL, 이미지 URL 외에 색상, 핏, 소재, 무드, 상황, 계절, 카테고리 태그를 저장한다.
- 태그는 자유 입력이 아니라 가능한 표준화된 taxonomy로 관리한다.
- 초기에는 사람이 검수 가능한 규모의 상품군부터 시작한다.

### 9.2 상품 이미지 캡셔닝

실제 판매 상품 이미지를 AI에게 설명하게 만들어 역으로 텍스트 캡션을 생성한다.

예:

상품 이미지 → "아이보리 컬러의 루즈핏 케이블 니트 가디건. 봄 데이트룩이나 캐주얼한 출근룩에 어울림."

이 캡션을 상품 DB에 저장하면 텍스트 프롬프트와 상품 매칭 정확도가 올라간다.

PRD 반영 항목:

- 상품 이미지마다 AI 생성 캡션을 저장한다.
- 캡션은 단순 설명형과 검색 최적화형을 분리할 수 있다.
- 예: "아이보리 루즈핏 니트 가디건"과 "봄 데이트, 캐주얼 출근룩, 여리여리한 무드에 어울리는 아이보리 루즈핏 니트 가디건"
- 캡션 품질을 사람이 샘플 검수하고, 잘못된 색상/소재/핏 인식은 수정한다.

### 9.3 프롬프트 역추출

판매 상품 또는 코디 이미지를 보고 "이 이미지를 생성하려면 어떤 프롬프트가 필요한가?"를 역으로 추출한다.

예:

상품 이미지/룩북 이미지 → AI 분석 → 생성 프롬프트 후보 생성

이 방식은 I.F.에 특히 유용하다. 사용자가 입력한 프롬프트와 실제 판매 상품에서 역추출한 프롬프트를 비교해 유사한 상품을 찾을 수 있기 때문이다.

PRD 반영 항목:

- 상품 이미지 또는 룩북 이미지에서 역프롬프트를 생성한다.
- 역프롬프트는 이미지 생성용과 검색 매칭용으로 구분한다.
- 이미지 생성용 역프롬프트는 모델에게 어떤 룩을 그리게 할지에 집중한다.
- 검색 매칭용 역프롬프트는 사용자가 실제로 입력할 만한 표현에 가깝게 만든다.
- 예: "꾸안꾸", "여리여리", "하체 커버", "벚꽃 데이트룩", "출근 가능한 캐주얼룩"

### 9.4 멀티모달 임베딩

텍스트와 이미지를 같은 벡터 공간에서 비교할 수 있는 멀티모달 임베딩을 사용한다.

기본 구조:

사용자 프롬프트 → 텍스트 임베딩  
상품 이미지 → 이미지 임베딩  
상품 설명/태그/캡션 → 텍스트 임베딩  
생성된 AI 룩 이미지 → 이미지 임베딩  

이후 벡터 DB에서 유사한 상품을 검색한다.

즉, "프롬프트와 상품", "생성 이미지와 상품 이미지", "룩 캡션과 상품 캡션"을 동시에 비교해야 한다.

PRD 반영 항목:

- 상품마다 텍스트 임베딩과 이미지 임베딩을 모두 저장한다.
- 사용자 프롬프트, 생성 이미지, 상품 캡션, 상품 이미지를 함께 비교하는 검색 구조를 설계한다.
- 단일 유사도 점수가 아니라 색상, 카테고리, 핏, 무드, 가격대 등 여러 점수를 조합한다.
- 검색 결과에는 "왜 이 상품이 추천되었는지"를 설명할 수 있는 근거를 남긴다.

#### B-path 매칭 임계값과 telemetry (백엔드 안전 보강 sync)

curated look DB 검색(B-path)과 AI 실시간 생성(A-path)의 분기 기준을 다음과 같이 못박는다. (docs/AI_PIPELINE.md §4, ADR-013 정합)

- 위 가중합 점수가 **0.70 이상**일 때만 B-path 적중으로 보고, 미달이면 A-path 실시간 생성으로 fallback한다. **0.70은 초기값**이며 출시 후 클릭/저장/구매 데이터로 튜닝한다(가중치 튜닝과 같은 루프). 임계값을 높이면 품질↑·적중률↓(생성 비용↑), 낮추면 적중률↑·오매칭 위험↑ — V0는 적중률 약 90% 목표와 품질의 절충점으로 0.70에서 시작한다.
- 매 생성 요청마다 B/A 분기 결과를 `generation_history.pipeline_source`(`curated_only`/`mixed`/`generated_only`, API 응답과 동일 enum)에 기록해 B/A 비율을 추적하고, B-path 최고 매칭 점수는 `generation_history.match_score`에 로깅해 임계값·가중치 튜닝 근거로 쓴다. 이 telemetry는 사용자에게 노출하지 않는다(내부 분석 전용).

### 9.5 Human Evaluation Loop

초기에는 AI가 자동으로 만든 태그와 매칭 결과를 사람이 직접 검수하는 과정이 필요하다.

특히 패션은 "비슷함"의 기준이 단순하지 않다. 색상은 비슷하지만 핏이 다르면 사용자는 다르다고 느낄 수 있고, 소재는 달라도 전체 무드가 같으면 만족할 수 있다.

따라서 초기에는 다음을 기록한다.

- 사용자가 좋아요/싫어요 한 결과
- 클릭한 상품
- 구매로 이어진 상품
- "비슷하지 않음"으로 표시한 상품
- 사용자가 수정한 프롬프트

이 피드백이 쌓이면 I.F.만의 패션 매칭 기준이 만들어진다.

PRD 반영 항목:

- 추천 결과에 대한 사용자 피드백 수집 구조를 설계한다.
- "비슷해요", "색은 좋은데 핏이 달라요", "가격대가 안 맞아요", "분위기가 달라요"처럼 패션 특화 피드백을 받을 수 있게 한다.
- 클릭, 저장, 공유, 구매 전환 데이터를 매칭 품질 평가 지표로 사용한다.
- 운영자가 매칭 실패 사례를 검수하고 태그/캡션/프롬프트를 개선할 수 있는 내부 관리 도구를 고려한다.

### 9.6 Trend-Informed Prompt Mapping

I.F.는 사용자가 정확한 의류명을 입력하지 않아도 작동해야 한다.

실제 사용자는 "린넨 셔츠", "세미와이드 슬랙스", "아이보리 반팔 니트"처럼 구체적으로 입력하기보다 다음과 같이 모호하고 상황적인 표현을 입력할 가능성이 높다.

- 여름철 남친룩
- 꾸안꾸 데이트룩
- 장마철 출근룩
- 여행 가서 사진 잘 나오는 옷
- 하객룩인데 너무 꾸민 느낌은 싫어
- 힙하지만 부담스럽지 않은 카페룩

이런 프롬프트는 정확한 상품명이나 카테고리가 아니라, 사회적 이미지, 상황, 계절, 무드가 섞인 표현이다. 따라서 I.F.는 이를 바로 상품 검색어로 사용하지 않고, 먼저 패션 의도로 분해해야 한다.

예:

"여름철 남친룩"

→ 성별: 남성  
→ 계절: 여름  
→ 무드: 깔끔함, 데일리, 호감형, 캐주얼  
→ 상황: 데이트, 주말 외출, 대학생/직장인 일상  
→ 예상 아이템: 린넨 셔츠, 반팔 니트, 와이드 슬랙스, 연청 데님, 버뮤다 팬츠, 미니멀 스니커즈, 샌들  
→ 예상 색상: 화이트, 스카이블루, 네이비, 베이지, 그레이  

이 과정에는 외부 검색/콘텐츠 데이터를 참고할 수 있다.

활용 가능한 데이터 소스:

- 네이버 데이터랩: 한국어 검색어 트렌드와 시즌성 확인
- Google Trends: 국내/글로벌 관심도 흐름 확인
- YouTube 검색 결과: 룩북, 하울, 코디 추천 영상에서 실제 아이템 조합 추출
- Pinterest Trends/검색 결과: 무드보드와 시각적 스타일 패턴 추출
- 네이버/구글 검색 결과: 블로그, 매거진, 쇼핑 콘텐츠에서 반복 등장하는 표현 추출
- I.F. 내부 데이터: 사용자의 클릭, 저장, 구매, 프롬프트 수정 데이터를 통한 보정

이 방식은 trend-informed query expansion 또는 intent-to-style mapping에 가깝다.

즉, I.F.는 사용자의 모호한 프롬프트를 다음과 같이 번역해야 한다.

> "여름철 남친룩" → "화이트/스카이블루 린넨 셔츠 + 세미와이드 슬랙스 + 미니멀 스니커즈 + 깔끔한 데이트룩 무드"

PRD 반영 항목:

- 모호한 상황형 프롬프트를 의류 속성으로 분해하는 intent parser를 설계한다.
- 검색량과 콘텐츠 결과를 참고해 시즌별/상황별 스타일 사전을 만든다.
- 외부 검색 결과를 그대로 복제하지 않고, 반복 등장하는 아이템, 색상, 핏, 무드, 상황 맥락만 추출한다.
- "남친룩", "꾸안꾸", "출근룩", "하객룩"처럼 한국어 패션 표현을 I.F. 내부 taxonomy와 연결한다.
- 외부 트렌드 데이터는 초기 해석 보조 수단으로 쓰고, 장기적으로는 I.F. 내부 클릭/저장/구매 데이터를 더 높은 우선순위로 둔다.
- 프롬프트 파싱(LLM + JSON schema) 결과를 그대로 신뢰하지 않고 한국어 패션 taxonomy enum 화이트리스트로 검증한다. 분해 결과의 {계절·무드·상황·아이템·색상·핏·소재·카테고리} 값을 상품 태그와 동일한 표준 enum에 대조해, 화이트리스트에 없는 값(LLM 환각·오타·자유 입력)은 버리거나 가장 가까운 enum으로 정규화한 뒤에만 검색·생성에 투입한다. 상품 측 태그 검증과 같은 화이트리스트를 공유해 프롬프트 어휘와 상품 어휘가 어긋나지 않게 한다(매칭 정확도 보장). 이 화이트리스트의 실제 값 목록은 9.9(한국어 패션 taxonomy enum 초안)이며 situation·mood·color·fit 4개 차원이다. (docs/AI_PIPELINE.md §6·부록 A 정합)

주의할 점:

- 네이버 데이터랩, Google Trends, Pinterest Trends는 검색량 절대값보다 상대적 관심도와 시즌성 파악에 더 적합하다.
- 플랫폼마다 유저 성향이 다르므로 하나의 플랫폼 결과를 절대 기준으로 삼으면 안 된다.
- "남친룩" 같은 표현은 시대와 계절에 따라 의미가 바뀌므로 주기적으로 갱신해야 한다.
- 트렌드 데이터를 활용하더라도 최종 추천은 실제 구매 가능한 상품과 연결되어야 한다.

### 9.7 Fine-Tuning Is Not The First Step

초기부터 이미지 생성 모델을 직접 학습시키거나 파인튜닝하는 것은 권장하지 않는다.

먼저 해야 할 일은 다음이다.

- 좋은 상품 데이터셋 만들기
- 상품 이미지 캡션 만들기
- 스타일 태그 체계 만들기
- 프롬프트 템플릿 만들기
- 생성 결과와 실제 상품 매칭 정확도 평가하기

이후 충분한 데이터가 쌓이면 LoRA, DreamBooth, ControlNet, IP-Adapter, fashion-specific embedding 등으로 확장할 수 있다.

초기에는 "모델을 학습시키는 것"보다 "모델이 이해하기 좋은 데이터와 프롬프트 구조를 만드는 것"이 더 중요하다.

### 9.8 Development Principle For Future PRD

향후 PRD와 MVP 설계에서 이 부분은 별도의 핵심 요구사항으로 다뤄야 한다.

개발 우선순위:

1. 상품 데이터 스키마 정의
2. 초기 상품 데이터 수집
3. 상품 이미지 캡셔닝
4. 스타일/무드/상황 태그 taxonomy 설계
5. 역프롬프트 생성
6. 한국어 상황형 프롬프트와 스타일 taxonomy 매핑
7. 외부 검색/트렌드 데이터 기반 시즌별 스타일 사전 구축
8. 텍스트/이미지 임베딩 저장
9. 프롬프트 기반 상품 검색
10. AI 생성 이미지 기반 상품 검색
11. 사용자 피드백 기반 매칭 개선
12. 충분한 데이터가 쌓인 후 모델 파인튜닝 검토

이 순서를 지키는 이유는 I.F.의 경쟁력이 범용 이미지 생성 모델 자체가 아니라 "사용자가 상상한 스타일을 실제 구매 가능한 국내 패션 상품으로 얼마나 잘 번역하는가"에 있기 때문이다.

즉, I.F.의 핵심 데이터 자산은 다음과 같다.

- 상품 이미지
- 상품 캡션
- 상품 속성 태그
- 상품별 역프롬프트
- 한국어 상황형 프롬프트 사전
- 외부 트렌드/검색 데이터에서 추출한 스타일 매핑
- 사용자 입력 프롬프트
- 생성된 룩 이미지
- 추천 결과
- 사용자 피드백
- 클릭/저장/구매 전환 데이터

이 데이터가 쌓이면 I.F.는 단순 AI 패션 이미지 생성 서비스가 아니라, 한국 여성 패션에 특화된 프롬프트-상품 연결 엔진으로 발전할 수 있다.

생성 이미지 영속화 (운영 메모): A-path 실시간 생성 룩 이미지는 생성 즉시 Supabase Storage에 저장하고, 룩 레코드(`looks.generated_image_url`)에는 OpenAI URL이 아니라 Storage 경로(서명 URL)를 보관한다. OpenAI 임시 URL은 24시간 후 만료되므로 그대로 두면 저장·공유 시점에 깨진다. A-path 생성 모델은 OpenAI GPT Image 2 · Medium · 1024×1024 운영 고정(ADR-003 참조). (docs/AI_PIPELINE.md §8 정합)

### 9.9 한국어 패션 taxonomy enum (V0 초안)

9.6에서 말한 "taxonomy enum 화이트리스트"의 실제 값 목록이다(정본: docs/AI_PIPELINE.md 부록 A — 양방향 거울). 상품 태그(9.1)와 프롬프트 의도 파싱이 **같은 화이트리스트**를 공유해야 프롬프트 어휘와 상품 어휘가 어긋나지 않는다.

- **범위**: 자유 어휘가 큰 4개 차원 — `situation`·`mood`·`color`·`fit`. 나머지는 이미 닫힌 enum이다 — `category`(상의/하의/원피스/아우터 4종)·`season`(봄/여름/가을/겨울 4종). `material`·`subcategory`는 별도 차원으로 추후 작성.
- **상태**: V0 초안. **아직 `.ts`로 옮기지 않는다** — Phase 4(taxonomy 설계) 진입 직전에 아래 "정제·운영 메모"를 반영해 `.ts` enum으로 변환한다. 기준은 한국 20-30대 여성 데일리 패션이며 런웨이·코스튬·과한 컨셉·남성 전용·아동·신발/가방/액세서리는 제외.
- **표기 규약**: `key`는 기계 안정적 ascii snake_case(.ts enum·상품 태그·파싱 정규화 키), 한국어 라벨은 표준 이름, 별칭은 사용자가 실제 입력하는 표현(파싱 시 key로 정규화), ★는 기존 9.1 고정 key(보존).

#### 상황 · `situation` — 94개

> 고정 key(9.1 보존, ★): `date`, `work`, `travel`, `sport`, `wedding_guest`, `picnic`

| `key` | 한국어 라벨 | 사용자 표현(별칭) | 비고 |

### 9.9.1 정제·운영 메모 (Phase 4 `.ts` 전환 전)

본 초안은 "누락보다 과수집" 원칙으로 망라적으로 담았다(빈도 데이터로 컷하는 게 누락을 채우는 것보다 쉽다). `.ts` enum 확정 전 다음을 정리한다. (docs/AI_PIPELINE.md 부록 A "정제·운영 메모"와 정합.)

- **교차차원 직교성 (적용 완료)**: 무드에 섞여 있던 상황 미러(`*_look`)·`tennis_core`는 제거하고 situation으로 일원화했다(한국어 별칭은 이미 situation에 보존됨). 꾸안꾸는 mood(`kkuankku`) 한 곳으로, 하객은 situation(`wedding_guest`) 한 곳으로 통일했다. `여리여리`는 mood(`yeori_yeori`, 분위기)와 fit(`wispy`, 실루엣)으로 의미를 분리해 동일 key 문자열 충돌을 제거했다.
- **`wedding_guest` 정규화 (PO 결정, 적용 완료)**: 하객 key는 본래 `gehakdaeng`이었으나 "하객"의 표준 로마자와 어긋나는 표기여서, PO 결정(2026-06-02)으로 `wedding_guest`로 정규화했다 — docs §1·부록 A·본 §9.9 동시 갱신. 정장형 변형은 `wedding_guest_formal`.
- **situation 상한 근접(94개)**: 50~100 범위 내이나 상한에 가깝다. `climbing`·`cycling`·`coming_of_age`·`market_flea`, 그리고 수영복 제외 겉옷군(`beach`·`water_park`·`swimming`)은 V0 4카테고리 상품 매칭이 빈약할 수 있어 V1 사용 로그로 통합·컷을 재검토한다.
- **fit 비(非)핏 항목 분리 후보**: 코디 조합 힌트(`loose_top`·`fitted_top`·`wide_bottom`·`slim_bottom`·`loose_fit_overall`·`fitted_overall`·`balanced_proportion`)와 체형 보완 효과(`tummy_cover`·`leg_lengthening`·`slim_look`)는 `products.fit` 단일값에 부적합하다 — 프롬프트 파싱 전용 또는 별도 필드(`proportion_hint`)로 분리할지 검토한다. (`hip_cover`는 고정 key라 유지.)
- **color 태깅 가이드**: 그레이지·뉴트럴 경계(`taupe`·`warm_gray`·`stone_gray`·`khaki_beige`)와 흙빛 적/오렌지(`brick`·`terracotta`·`rust`)는 텍스트 설명만으로 분별이 어렵다 — 상품 태깅 가이드에 대표 hex 샘플을 붙인다. `multicolor`는 단일 색 원칙의 예외(escape hatch, 진짜 다색일 때만). `gold`·`silver`의 강한 메탈릭 광택 차단은 색상값이 아니라 material/finish 또는 생성 가드에서 통제한다.
- **LLM 정규화 우선순위**: 인접 항목(`work`/`office_business`/`office_casual`, chic 계열 등)은 사용자 입력이 모호할 때 어느 enum으로 정규화할지 `/api/prompts/interpret` 프롬프트에 우선순위를 명시한다(9.6).

## 10. Competitive Landscape And Positioning

I.F.는 완전히 비어 있는 시장에 들어가는 것이 아니다. 해외에는 AI 패션 디스커버리 서비스가 등장했고, 국내 주요 패션 플랫폼도 AI 검색과 추천 기능을 강화하고 있다.

중요한 것은 "비슷한 기능이 있는가"가 아니라 "사용자의 어떤 시작점과 어떤 범위의 선택지를 해결하는가"다.

### 10.3 Global Brand-Owned AI References

- 브랜드는 AI 기능을 자사 카탈로그 전환율을 높이는 도구로 활용하고 있다.

- I.F.는 특정 브랜드 안에 갇히지 않고 여러 브랜드/쇼핑몰을 가로지르는 독립형 탐색 레이어를 지향한다.

### 10.4 I.F.'s Empty Space

I.F.가 점유해야 할 빈자리는 다음 네 가지가 겹치는 영역이다.

- 텍스트 프롬프트 기반 패션 탐색
- AI 이미지/룩 시각화
- 여러 쇼핑몰과 브랜드를 가로지르는 상품 연결
- 한국 여성 패션 맥락에 특화된 추천

이를 한 문장으로 정리하면 다음과 같다.

> I.F.는 사용자가 상상한 스타일을 말로 입력하면, AI가 그 스타일을 시각화하고 여러 국내 패션 쇼핑몰/브랜드 중 실제 구매 가능한 선택지로 연결해주는 독립형 AI 패션 탐색 레이어다.

### 10.5 Positioning Advice

- 핵심 확장 문장: If you can imagine, you can wear it.
- 사용자 약속: "원하는 스타일을 말하면, AI가 룩으로 보여주고 실제 살 수 있는 옷으로 연결한다."
- 경쟁 차별점: "한 쇼핑몰 안에서 찾는 것이 아니라, 여러 브랜드와 플랫폼을 가로질러 최적의 선택지를 찾는다."
- 감성 차별점: "검색창이 아니라 AI 패션 디렉터와 대화하는 경험."
- 데이터 차별점: "한국 여성 패션에 특화된 프롬프트-상품 매칭 데이터."

피해야 할 포지션:

- "지그재그 렌즈의 다른 버전"
- "무신사/에이블리 상품 추천 챗봇"
- "AI로 예쁜 옷 이미지만 만들어주는 앱"
- "가상 피팅 앱"

I.F.의 가장 강한 문장은 "사진 속 옷을 찾아준다"보다 "상상한 옷을 실제 살 수 있는 선택지로 바꿔준다"에 가깝다. 이미지 업로드는 이 문장을 보조하는 기능이어야 한다.

### 10.6 Positioning Questions For PRD

PRD 작성 전 추가로 정해야 할 질문은 다음과 같다.

1. I.F.가 처음 연결할 상품 범위는 "브랜드 자사몰" 중심인가, "여러 플랫폼 통합" 중심인가?
2. 사용자가 I.F.를 떠올리는 첫 상황은 "오늘 뭐 입지?"인가, "이런 옷 사고 싶다"인가, "저 옷 어디 거지?"인가?
3. AI 생성 이미지는 결과의 중심인가, 아니면 상품 탐색을 돕는 중간 시각화인가?
4. I.F.는 구매 전환을 최우선으로 볼 것인가, 저장/공유/무드보드 형성을 먼저 볼 것인가?
5. 유료 기능은 이미지 업로드 검색, 더 많은 결과, 고급 필터, 개인화 프로필 중 무엇부터 시작할 것인가?
6. 상품 추천에서 "정확히 비슷함"과 "스타일이 어울림" 중 무엇을 더 우선할 것인가?
7. 지그재그/무신사/에이블리와 비교될 때, I.F.가 반복해서 말할 한 문장은 무엇인가?

## 11. Key Risks

### 11.1 Technical Risk

- AI 이미지가 실제 판매 상품과 너무 다르게 생성될 수 있다.
- 체형 조건을 이미지에 일관되게 반영하기 어려울 수 있다.
- 상품 매칭 정확도가 낮으면 사용자가 신뢰하지 않는다.
- 패션 이미지는 디테일, 핏, 소재감이 중요하므로 일반 이미지 생성 모델의 한계가 드러날 수 있다.

### 11.2 Data Risk

- 상품 데이터 확보가 어렵다.
- 브랜드 자사몰마다 데이터 구조가 다르다.
- 가격, 재고, 옵션 변동을 실시간으로 반영하기 어렵다.
- 크롤링은 법적/운영 리스크가 있으므로 장기적으로 제휴 또는 어필리에이트 구조가 필요하다.

### 11.3 Legal And Privacy Risk

- 이미지 업로드 기능은 사용자가 올리는 사진의 출처와 저작권 문제가 있을 수 있다.
- 셀럽 얼굴을 기반으로 새 이미지를 생성하는 기능은 피해야 한다.
- 사용자 얼굴이나 신체 사진을 저장하는 기능은 개인정보/생체정보 리스크가 크다.
- V0에서는 얼굴 기반 기능을 제외하거나 저장하지 않는 구조로 설계하는 것이 안전하다.

### 11.4 Product Risk

- "다 되는 서비스"로 시작하면 포지션이 흐려질 수 있다.
- V0에서는 텍스트 프롬프트 기반 패션 이미지/룩 생성과 실제 상품 연결에 집중해야 한다.
- 이미지 업로드, 가상 피팅, 셀럽/인플루언서 룩 검색은 단계적으로 확장한다.

### 11.5 Competitive Risk

- 지그재그, 무신사, 에이블리 등 기존 플랫폼이 유사 기능을 자체 강화할 수 있다.
- 기존 플랫폼은 상품 데이터, 사용자, 구매 전환 데이터를 이미 보유하고 있다.
- I.F.가 방어해야 할 지점은 특정 플랫폼 내부 검색이 아니라, 여러 플랫폼을 가로지르는 프롬프트 기반 탐색 경험이다.
- 범용 LLM이 쇼핑 기능을 강화할 수 있지만, 한국 여성 패션 카탈로그와 실제 구매 가능한 상품 연결은 I.F.의 데이터 자산으로 방어해야 한다.

## 12. Positioning Candidates

브랜드 메시지:

- Wear what you imagine.
- If you can imagine, you can wear it.
- Dress what you imagine.
- 상상한 대로 입다.
- 옷을 찾는 시간을 줄이고, 상상한 스타일에 가까워지는 AI 패션 도구.

제품 설명 후보:

- I.F.는 사용자가 상상한 스타일을 AI 이미지로 시각화하고, 실제 구매 가능한 옷으로 연결하는 패션 커머스 플랫폼이다.
- I.F.는 텍스트 프롬프트로 원하는 스타일을 말하면, AI가 룩을 만들고 국내 브랜드 상품 중 가장 가까운 옷을 찾아주는 서비스다.
- I.F.는 ChatGPT처럼 대화하고, Pinterest처럼 발견하고, 쇼핑몰처럼 구매로 이어지는 AI 패션 인터페이스다.
- I.F.는 지그재그처럼 이미 본 옷을 찾는 데서 출발하지 않고, 사용자가 상상한 스타일을 말로 만들고 실제 구매 가능한 선택지로 연결하는 AI 패션 도구다.
- I.F.는 하나의 쇼핑몰 검색창이 아니라, 여러 국내 패션 브랜드와 플랫폼을 가로지르는 AI 스타일 탐색 레이어다.

## 13. Next Decisions

PRD 작성 전에 확정해야 할 질문은 다음과 같다.

1. V0에서 AI 이미지는 "전신 착장 이미지"까지 생성할 것인가, 아니면 무드보드/룩 카드 중심으로 시작할 것인가?
2. 초기 상품 카테고리는 어디까지 포함할 것인가?
3. 국내 브랜드 자사몰 중 어떤 브랜드군을 우선 수집할 것인가?
4. 상품 매칭의 성공 기준은 무엇인가?
5. 사용자가 프롬프트를 쉽게 입력하도록 어떤 질문/필터를 제공할 것인가?
6. 무료/유료 기능을 어떻게 나눌 것인가?
7. 이미지 업로드 기반 검색은 어떤 결제 단계에서 제공할 것인가?
8. 지그재그 직잭렌즈와 비교될 때, I.F.가 반복해서 말할 핵심 차별화 문장은 무엇인가?
9. I.F.는 초기에는 브랜드 자사몰 중심으로 갈 것인가, 플랫폼 통합 검색 중심으로 갈 것인가?
10. 사진 업로드 기능은 "영감 수집"에 가까운가, "상품 검색"에 가까운가?

## 15. Working Assumption For PRD

현재 기준 PRD의 기본 전제는 다음과 같다.

I.F.의 V0는 "텍스트 프롬프트로 상상한 여성 패션 스타일을 AI가 시각화하고, 국내 브랜드 상품 중 유사한 옷을 찾아 연결해주는 서비스"다.

이미지 업로드 검색, 사용자 닮은 AI 모델, 얼굴 기반 가상 피팅은 장기 비전으로 남기되, V0의 핵심 범위에서는 제외하거나 유료 확장 기능으로 다룬다.
