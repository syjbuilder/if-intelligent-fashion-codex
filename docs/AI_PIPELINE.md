# AI Pipeline

> 출처: `기획/If discovery summary.md` §9 (Prompt-Based Generation Accuracy) 압축 정리.
> 본 문서는 I.F. AI 파이프라인의 정식 청사진이다. TRD §10 (AI Stack) + ADR-003·005·007과 정합.

## 핵심 원칙

> **초기에는 모델 파인튜닝보다 상품 데이터 구조화와 프롬프트-상품 매칭 데이터 자산 구축이 먼저다.**

I.F의 장기 경쟁력은 범용 이미지 생성 모델이 아니라 **"사용자가 상상한 스타일을 실제 구매 가능한 국내 패션 상품으로 얼마나 잘 번역하는가"** 에 있다. 이 번역 품질을 좌우하는 자산은 모델 weight가 아니라 다음 5개 데이터 레버다.

## 품질을 결정하는 5개 레버

1. **프롬프트 의도 파싱 품질** — "여름 데이트룩" → {계절·무드·상황·아이템·색상} 분해
2. **상품 데이터 구조화** — 색상·핏·소재·무드·상황·계절 표준 enum 태그
3. **상품 이미지 캡셔닝** — AI 자동 생성 + 사람 검수
4. **멀티모달 임베딩** — 텍스트·이미지를 같은 벡터 공간에서 비교
5. **사용자 피드백 루프** — 패션 특화 피드백("색은 좋은데 핏이 달라요" 등)

## §1. 상품 데이터 구조화

실제 판매 상품을 단순 이미지·상품명으로만 보지 않고 **패션 속성 단위로 분해**한다.

### 필수 속성 (표준 enum, 자유 입력 금지)

| 속성 | 값 예시 |
|---|---|
| 카테고리 | top, bottom, dress, outer (V0 한정 — 신발·가방·액세서리 제외) |
| 세부 카테고리 | sweatshirt, crop_tee, wide_denim, flare_skirt 등 |
| 색상 | navy, ivory, light_blue 등 — Pantone 그룹화 가능 |
| 핏 | over, slim, hip_cover, semi_wide, high_waist 등 |
| 소재 | cotton, nylon, denim, knit, linen 등 |
| 무드 | casual, lovely, minimal, street, ballet_core, old_money 등 |
| 상황 | date, work, travel, sport, gehakdaeng(하객), picnic 등 |
| 계절 | spring, summer, fall, winter |

### docs/DATA_MODEL.md `products` 테이블 매핑

- `category` / `subcategory` / `color` / `fit` / `material` — 단일 값
- `mood_tags` / `season_tags` / `situation_tags` — `text[]` (중복 가능)
- 태그는 enum 검증 (서버에서 화이트리스트 통과 후 insert)

### V0 시작 범위

500개 curated look + 룩에 매핑된 상품 (룩당 평균 3-5개 = 약 1500-2500개 상품). 사람이 직접 검수 가능한 규모.

## §2. 상품 이미지 캡셔닝

실제 판매 상품 이미지를 AI에게 설명하게 만들어 **역으로 텍스트 캡션 생성**.

### 캡션 종류 (둘 다 저장)

1. **단순 설명형**: "아이보리 컬러의 루즈핏 케이블 니트 가디건."
2. **검색 최적화형**: "봄 데이트, 캐주얼 출근룩, 여리여리한 무드에 어울리는 아이보리 루즈핏 니트 가디건."

### 운영

- AI(GPT-4V·Claude Vision 등)로 자동 생성
- 사람이 샘플 검수 — 잘못된 색상/소재/핏 인식 수정
- 캡션은 후속 임베딩(§4)의 입력으로 사용

### 저장 위치

V0에서는 `products` 테이블에 `caption_simple` / `caption_searchable` 컬럼 추가 권장 (DATA_MODEL.md 확장 시 반영).

## §3. 프롬프트 역추출

상품·룩북 이미지에서 **"이 이미지를 생성하려면 어떤 프롬프트가 필요한가"** 를 역으로 추출.

### 두 종류 분리

1. **이미지 생성용 역프롬프트** — 모델에게 룩을 그리게 할 영문/한글 디테일 프롬프트
2. **검색 매칭용 역프롬프트** — 사용자가 실제로 입력할 만한 표현 ("꾸안꾸", "여리여리", "하체 커버", "벚꽃 데이트룩")

### 활용

- 사용자 프롬프트 ↔ 역프롬프트 유사도로 상품 매칭 가능
- curated look DB 구축 시 핵심 자산

---

## §4. 멀티모달 임베딩

텍스트와 이미지를 **같은 벡터 공간**에서 비교 가능하게 한다.

### 임베딩 대상 (4종)

```
사용자 프롬프트   → 텍스트 임베딩
상품 이미지       → 이미지 임베딩
상품 설명/태그/캡션 → 텍스트 임베딩
생성된 AI 룩 이미지 → 이미지 임베딩
```

### 비교 방식

벡터 DB(예: pgvector·Pinecone·Weaviate)에 저장 후 4가지 비교:
- 사용자 프롬프트 ↔ 상품 캡션
- 사용자 프롬프트 ↔ 상품 이미지
- 생성된 AI 룩 이미지 ↔ 상품 이미지
- 생성된 AI 룩 이미지 ↔ 상품 캡션

### Ensemble 매칭 점수 (Daydream 영감 — 도메인 전문 모델 합주)

**단일 유사도 점수 X. 차원별 점수를 따로 매기고 가중합.**

| 차원 | 가중치(예시) | 설명 |
|---|---|---|
| 색상 일치 | 0.20 | color 태그·픽셀 분포 |
| 카테고리 일치 | 0.25 | top/bottom/dress 등 |
| 핏 일치 | 0.15 | fit 태그·실루엣 임베딩 |
| 무드 일치 | 0.20 | mood 태그·캡션 유사도 |
| 가격대 일치 | 0.10 | 사용자 budget vs price |
| 시즌·상황 일치 | 0.10 | season·situation 태그 |

가중치는 V0 출시 후 사용자 클릭/저장/구매링크 클릭 데이터로 튜닝.

### B-path 매칭 임계값 (초기값 0.70)

curated look DB 검색(B-path)에서 위 가중합 점수가 **0.70 이상**일 때만 B-path 적중으로 간주하고, 미달이면 A-path(실시간 생성)로 fallback한다.

- **0.70은 초기값** — 출시 후 사용자 피드백·클릭/저장 데이터로 튜닝한다(가중치 튜닝과 동일 루프).
- 임계값을 높이면 B-path 품질↑·적중률↓(생성 비용↑), 낮추면 적중률↑·오매칭 위험↑. V0는 적중률(약 90% 목표)과 품질의 절충점으로 0.70에서 시작.

### B/A 비율·매칭 점수 telemetry 로깅

파이프라인 튜닝의 근거 데이터를 매 생성 요청마다 적재한다.

- **B-path / A-path 분기 기록** — `docs/DATA_MODEL.md` `generation_history.pipeline_source`에 분기 결과(`curated_only`/`mixed`/`generated_only` — API 응답 `pipeline_source`와 동일 enum)를 남겨 B/A 비율을 추적한다.
- **매칭 점수 기록** — B-path 후보의 최고 가중합 점수를 `generation_history.match_score`에 로깅해 임계값(0.70)·가중치 튜닝 근거로 사용한다(차원별 세부 점수는 V0 범위 밖, 데이터 축적 후 검토).
- 이 telemetry는 사용자에게 노출하지 않는다(ADR-012 — `pipeline_source`는 telemetry 전용, UI 노출 X).

### V0 우선 적용

V0 출시 시점에는 멀티모달 임베딩보다 **curated look DB의 의미적 검색**(태그 + 캡션 키워드 매칭)이 우선. 임베딩은 V0.5 데이터 축적 후 도입.

## §5. Human Evaluation Loop

패션은 "비슷함"의 기준이 단순하지 않다. 색상은 비슷한데 핏이 다르면 사용자는 "다르다"고 느낄 수 있고, 소재는 달라도 전체 무드가 같으면 만족할 수 있다.

### 수집할 패션 특화 피드백

기본 좋아요/싫어요만으로는 부족. 다음을 명시적 옵션으로 제공:

| 피드백 항목 | 의미 |
|---|---|
| "비슷해요" | 매칭 성공 (positive signal) |
| "색은 좋은데 핏이 달라요" | 핏 차원 불일치 |
| "가격대가 안 맞아요" | budget 필터링 오류 |
| "분위기가 달라요" | mood 차원 불일치 |
| "전혀 다르네요" | 명시적 negative signal |

### 운영자 검수 도구

- 매칭 실패 사례를 운영자가 검수
- 태그·캡션·역프롬프트를 수정해 재학습 데이터로 사용
- V0에서는 어드민 화면에서 수동 처리, V1 이상에서 자동화

### 정량 지표

- 클릭률
- 저장률
- 공유율
- 구매 링크 클릭률 (V0 핵심 KPI — 자체 결제 X이므로)

## §6. 한국어 상황형 프롬프트 매핑

I.F는 사용자가 정확한 의류명을 입력하지 않아도 작동해야 한다.

### 실제 사용자 입력 패턴

```
- 여름철 남친룩
- 꾸안꾸 데이트룩
- 장마철 출근룩
- 여행 가서 사진 잘 나오는 옷
- 하객룩인데 너무 꾸민 느낌은 싫어
- 힙하지만 부담스럽지 않은 카페룩
```

이런 프롬프트는 사회적 이미지·상황·계절·무드가 섞인 표현. **바로 상품 검색어로 사용 X.** 먼저 패션 의도로 분해해야 한다.

### 분해 예시

```
"여름철 남친룩"
  → 성별: 남성
  → 계절: 여름
  → 무드: 깔끔함, 데일리, 호감형, 캐주얼
  → 상황: 데이트, 주말 외출, 대학생/직장인 일상
  → 예상 아이템: 린넨 셔츠, 반팔 니트, 와이드 슬랙스, 연청 데님, 버뮤다 팬츠, 미니멀 스니커즈, 샌들
  → 예상 색상: 화이트, 스카이블루, 네이비, 베이지, 그레이
```

### enum 화이트리스트 검증 (파싱 결과 정합)

프롬프트 의도 파싱(LLM + JSON schema) 결과를 **그대로 신뢰하지 않고** 한국어 패션 taxonomy enum 화이트리스트로 검증한다.

- 분해 결과의 {계절·무드·상황·아이템·색상·핏·소재·카테고리} 값을 §1 표준 enum(`products` 태그와 동일 화이트리스트)에 대조한다.
- 화이트리스트에 없는 값(LLM hallucination·오타·자유 입력)은 버리거나 가장 가까운 enum으로 정규화한 뒤에만 B-path 검색·A-path 생성에 투입한다.
- §1의 상품 태그 enum 검증과 **같은 화이트리스트**를 공유해, 프롬프트 측과 상품 측 어휘가 어긋나지 않게 한다(매칭 정확도 보장).

### 외부 trend data 활용

| 소스 | 용도 |
|---|---|
| 네이버 데이터랩 | 한국어 검색 트렌드·시즌성 |
| Google Trends | 국내/글로벌 관심도 비교 |
| YouTube 검색 결과 | 룩북·하울·코디 추천 영상에서 아이템 조합 추출 |
| Pinterest Trends | 무드보드·시각 스타일 패턴 |
| 네이버/구글 검색 결과 | 블로그·매거진 반복 등장 표현 |
| I.F 내부 데이터 | 클릭/저장/구매링크 클릭 (시간 지나면 가장 신뢰도 높음) |

### 주의

- 외부 trend는 **상대적 관심도**·**시즌성** 파악용. 절대값 X
- 플랫폼마다 사용자 성향 다름 — 하나에 의존 금지
- "남친룩" 등 표현은 시대·계절에 따라 의미 변동 — **주기적 갱신**
- trend data를 그대로 복제 X. 반복 등장하는 아이템·색상·핏·무드·상황 맥락만 추출
- 최종 추천은 항상 실제 구매 가능한 상품과 연결되어야 함

## §7. Fine-Tuning은 첫 단계가 아님

초기부터 이미지 생성 모델을 직접 학습/파인튜닝하는 것은 권장하지 않는다.

### 먼저 해야 할 일

1. 좋은 상품 데이터셋 만들기 (§1)
2. 상품 이미지 캡션 만들기 (§2)
3. 스타일 태그 체계 만들기 (§1)
4. 프롬프트 템플릿 만들기 (§3)
5. 생성 결과와 실제 상품 매칭 정확도 평가하기 (§5)

### 충분한 데이터가 쌓인 후

V1 이상에서 다음 검토 가능:
- LoRA (스타일별 어댑터)
- DreamBooth (특정 룩 재현)
- ControlNet (포즈·구도 제어)
- IP-Adapter (참조 이미지 기반)
- fashion-specific embedding

**초기에는 "모델을 학습시키는 것"보다 "모델이 이해하기 좋은 데이터·프롬프트 구조를 만드는 것"이 우선.**

## §8. 개발 우선순위 (1 → 12)

V0 부트스트랩부터 V1+까지 순서대로:

| 순서 | 작업 | V0/V0.5/V1 |
|---|---|---|
| 1 | 상품 데이터 스키마 정의 | V0 (docs/DATA_MODEL.md 완료) |
| 2 | 초기 상품 데이터 수집 | V0 — 사용자분 큐레이션 50→500개 |
| 3 | 상품 이미지 캡셔닝 | V0 — AI 자동 + 사람 검수 |
| 4 | 스타일/무드/상황 taxonomy 설계 | V0 — enum 화이트리스트 |
| 5 | 역프롬프트 생성 | V0 — curated look 구축 시 |
| 6 | 한국어 상황형 프롬프트 → taxonomy 매핑 | V0 — `/api/prompts/interpret`의 핵심 |
| 7 | 외부 trend data 기반 시즌별 스타일 사전 | V0 — 시즌 데모 프롬프트(Explore 피드 구성) |
| 8 | 텍스트/이미지 임베딩 저장 | **V0.5** (V0는 태그·캡션 기반 검색으로 시작) |
| 9 | 프롬프트 기반 상품 검색 | V0 — B-path (curated 검색) |
| 10 | AI 생성 이미지 기반 상품 검색 | V0.5 (A-path 정확도 향상) |
| 11 | 사용자 피드백 기반 매칭 개선 | V0.5 — Human eval loop 운영 |
| 12 | 모델 파인튜닝 검토 | V1 이상 |

이 순서를 지키는 이유: I.F의 경쟁력은 **범용 이미지 생성 모델 자체가 아니라 "사용자가 상상한 스타일을 실제 구매 가능한 국내 패션 상품으로 얼마나 잘 번역하는가"**에 있기 때문.

### B-path / A-path 운영 메모

- **B-path (curated 검색, 약 90%)** — §4 가중합 점수 ≥ 0.70 시 적중. 미달이면 A-path로 fallback.
- **A-path (실시간 AI 생성, fallback)** — **OpenAI GPT Image 2 · Medium · 1024×1024 고정**($0.053 ≈ 74원/이미지). 모델·quality·해상도는 운영 기준으로 고정이며 변경은 ADR-003에서만 다룬다. → `docs/ADR.md` ADR-003 참조.

### 생성 이미지 영속화

A-path로 생성한 룩 이미지는 **생성 즉시 Supabase Storage에 저장**하고, `docs/DATA_MODEL.md` `looks.generated_image_url`에는 OpenAI URL이 아니라 Storage 경로(서명 URL)를 보관한다 — OpenAI 임시 URL은 24시간 후 만료되므로 그대로 두면 저장·공유 시점에 깨진다.

## I.F의 핵심 데이터 자산

```
- 상품 이미지
- 상품 캡션
- 상품 속성 태그
- 상품별 역프롬프트
- 한국어 상황형 프롬프트 사전
- 외부 trend 데이터에서 추출한 스타일 매핑
- 사용자 입력 프롬프트
- 생성된 룩 이미지
- 추천 결과
- 사용자 피드백
- 클릭/저장/구매 전환 데이터
```

이 데이터가 쌓이면 I.F는 단순 AI 패션 이미지 생성 서비스가 아니라 **한국 여성 패션에 특화된 프롬프트-상품 연결 엔진**으로 발전할 수 있다.
