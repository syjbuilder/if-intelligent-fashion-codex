# AI Pipeline

> 출처: `기획/If discovery summary.md` §9 (Prompt-Based Generation Accuracy) 압축 정리.
> 본 문서는 I.F. AI 파이프라인의 정식 청사진이다. TRD §10 (AI Stack) + ADR-003·005·007과 정합.

## 핵심 원칙

> **초기에는 모델 파인튜닝보다 상품 데이터 구조화와 프롬프트-상품 매칭 데이터 자산 구축이 먼저다.**

I.F의 장기 경쟁력은 범용 이미지 생성 모델이 아니라 **"사용자가 상상한 스타일을 실제 구매 가능한 국내 패션 상품으로 얼마나 잘 번역하는가"** 에 있다. 이 번역 품질을 좌우하는 자산은 모델 weight가 아니라 다음 5개 데이터 레버다.

## 품질을 결정하는 5개 레버

1. **프롬프트 의도 파싱 품질** — "여름 데이트룩" → {계절·무드·상황·아이템·색상} 분해
2. **상품 데이터 구조화** — 색상·핏·소재·무드·상황·계절 표준 enum 태그
3. **상품 이미지 캡셔닝** — AI 자동 생성 + 사람 검수
4. **멀티모달 임베딩** — 텍스트·이미지를 같은 벡터 공간에서 비교
5. **사용자 피드백 루프** — 패션 특화 피드백("색은 좋은데 핏이 달라요" 등)

## §1. 상품 데이터 구조화

실제 판매 상품을 단순 이미지·상품명으로만 보지 않고 **패션 속성 단위로 분해**한다.

### 필수 속성 (표준 enum, 자유 입력 금지)

| 속성 | 값 예시 |
|---|---|
| 카테고리 | top, bottom, dress, outer (V0 한정 — 신발·가방·액세서리 제외) |
| 세부 카테고리 | sweatshirt, crop_tee, wide_denim, flare_skirt 등 |
| 색상 | navy, ivory, light_blue 등 — Pantone 그룹화 가능 |
| 핏 | over, slim, hip_cover, semi_wide, high_waist 등 |
| 소재 | cotton, nylon, denim, knit, linen 등 |
| 무드 | casual, lovely, minimal, street, ballet_core, old_money 등 |
| 상황 | date, work, travel, sport, wedding_guest(하객), picnic 등 |
| 계절 | spring, summer, fall, winter |

### docs/DATA_MODEL.md `products` 테이블 매핑

- `category` / `subcategory` / `color` / `fit` / `material` — 단일 값
- `mood_tags` / `season_tags` / `situation_tags` — `text[]` (중복 가능)
- 태그는 enum 검증 (서버에서 화이트리스트 통과 후 insert)

### V0 시작 범위

500개 curated look + 룩에 매핑된 상품 (룩당 평균 3-5개 = 약 1500-2500개 상품). 사람이 직접 검수 가능한 규모.

## §2. 상품 이미지 캡셔닝

실제 판매 상품 이미지를 AI에게 설명하게 만들어 **역으로 텍스트 캡션 생성**.

### 캡션 종류 (둘 다 저장)

1. **단순 설명형**: "아이보리 컬러의 루즈핏 케이블 니트 가디건."
2. **검색 최적화형**: "봄 데이트, 캐주얼 출근룩, 여리여리한 무드에 어울리는 아이보리 루즈핏 니트 가디건."

### 운영

- AI(GPT-4V·Claude Vision 등)로 자동 생성
- 사람이 샘플 검수 — 잘못된 색상/소재/핏 인식 수정
- 캡션은 후속 임베딩(§4)의 입력으로 사용

### 저장 위치

V0에서는 두 캡션을 먼저 `data/curated/products.csv` 수집 템플릿(§9)에 선수집한다. `products` 테이블 `caption_simple` / `caption_searchable` 컬럼 **추가는 V0 부트스트랩(`002_init_looks_products.sql`)에서 실제 수집 데이터로 타입·길이를 검증한 뒤 확정**한다 — frozen 스키마(10테이블)를 데이터 없이 미리 열지 않는다. 결정 근거는 `docs/DATA_MODEL.md` §15.3 메모 참조.

## §3. 프롬프트 역추출

상품·룩북 이미지에서 **"이 이미지를 생성하려면 어떤 프롬프트가 필요한가"** 를 역으로 추출.

### 두 종류 분리

1. **이미지 생성용 역프롬프트** — 모델에게 룩을 그리게 할 영문/한글 디테일 프롬프트
2. **검색 매칭용 역프롬프트** — 사용자가 실제로 입력할 만한 표현 ("꾸안꾸", "여리여리", "하체 커버", "벚꽃 데이트룩")

### 활용

- 사용자 프롬프트 ↔ 역프롬프트 유사도로 상품 매칭 가능
- curated look DB 구축 시 핵심 자산

## §4. 멀티모달 임베딩

텍스트와 이미지를 **같은 벡터 공간**에서 비교 가능하게 한다.

### 임베딩 대상 (4종)

```
사용자 프롬프트   → 텍스트 임베딩
상품 이미지       → 이미지 임베딩
상품 설명/태그/캡션 → 텍스트 임베딩
생성된 AI 룩 이미지 → 이미지 임베딩
```

### 비교 방식

벡터 DB(예: pgvector·Pinecone·Weaviate)에 저장 후 4가지 비교:
- 사용자 프롬프트 ↔ 상품 캡션
- 사용자 프롬프트 ↔ 상품 이미지
- 생성된 AI 룩 이미지 ↔ 상품 이미지
- 생성된 AI 룩 이미지 ↔ 상품 캡션

### Ensemble 매칭 점수 (Daydream 영감 — 도메인 전문 모델 합주)

**단일 유사도 점수 X. 차원별 점수를 따로 매기고 가중합.**

| 차원 | 가중치(예시) | 설명 |
|---|---|---|
| 색상 일치 | 0.20 | color 태그·픽셀 분포 |
| 카테고리 일치 | 0.25 | top/bottom/dress 등 |
| 핏 일치 | 0.15 | fit 태그·실루엣 임베딩 |
| 무드 일치 | 0.20 | mood 태그·캡션 유사도 |
| 가격대 일치 | 0.10 | 사용자 budget vs price |
| 시즌·상황 일치 | 0.10 | season·situation 태그 |

가중치는 V0 출시 후 사용자 클릭/저장/구매링크 클릭 데이터로 튜닝.

### B-path 매칭 임계값 (초기값 0.70)

curated look DB 검색(B-path)에서 위 가중합 점수가 **0.70 이상**일 때만 B-path 적중으로 간주하고, 미달이면 A-path(실시간 생성)로 fallback한다.

- **0.70은 초기값** — 출시 후 사용자 피드백·클릭/저장 데이터로 튜닝한다(가중치 튜닝과 동일 루프).
- 임계값을 높이면 B-path 품질↑·적중률↓(생성 비용↑), 낮추면 적중률↑·오매칭 위험↑. V0는 적중률(약 90% 목표)과 품질의 절충점으로 0.70에서 시작.

### B/A 비율·매칭 점수 telemetry 로깅

파이프라인 튜닝의 근거 데이터를 매 생성 요청마다 적재한다.

- **B-path / A-path 분기 기록** — `docs/DATA_MODEL.md` `generation_history.pipeline_source`에 분기 결과(`curated_only`/`mixed`/`generated_only` — API 응답 `pipeline_source`와 동일 enum)를 남겨 B/A 비율을 추적한다.
- **매칭 점수 기록** — B-path 후보의 최고 가중합 점수를 `generation_history.match_score`에 로깅해 임계값(0.70)·가중치 튜닝 근거로 사용한다(차원별 세부 점수는 V0 범위 밖, 데이터 축적 후 검토).
- 이 telemetry는 사용자에게 노출하지 않는다(ADR-012 — `pipeline_source`는 telemetry 전용, UI 노출 X).

### V0 우선 적용

V0 출시 시점에는 멀티모달 임베딩보다 **curated look DB의 의미적 검색**(태그 + 캡션 키워드 매칭)이 우선. 임베딩은 V0.5 데이터 축적 후 도입.

## §5. Human Evaluation Loop

패션은 "비슷함"의 기준이 단순하지 않다. 색상은 비슷한데 핏이 다르면 사용자는 "다르다"고 느낄 수 있고, 소재는 달라도 전체 무드가 같으면 만족할 수 있다.

### 수집할 패션 특화 피드백

기본 좋아요/싫어요만으로는 부족. 다음을 명시적 옵션으로 제공:

| 피드백 항목 | 의미 |
|---|---|
| "비슷해요" | 매칭 성공 (positive signal) |
| "색은 좋은데 핏이 달라요" | 핏 차원 불일치 |
| "가격대가 안 맞아요" | budget 필터링 오류 |
| "분위기가 달라요" | mood 차원 불일치 |
| "전혀 다르네요" | 명시적 negative signal |

### 운영자 검수 도구

- 매칭 실패 사례를 운영자가 검수
- 태그·캡션·역프롬프트를 수정해 재학습 데이터로 사용
- V0에서는 어드민 화면에서 수동 처리, V1 이상에서 자동화

### 정량 지표

- 클릭률
- 저장률
- 공유율
- 구매 링크 클릭률 (V0 핵심 KPI — 자체 결제 X이므로)

## §6. 한국어 상황형 프롬프트 매핑

I.F는 사용자가 정확한 의류명을 입력하지 않아도 작동해야 한다.

### 실제 사용자 입력 패턴

```
- 여름철 남친룩
- 꾸안꾸 데이트룩
- 장마철 출근룩
- 여행 가서 사진 잘 나오는 옷
- 하객룩인데 너무 꾸민 느낌은 싫어
- 힙하지만 부담스럽지 않은 카페룩
```

이런 프롬프트는 사회적 이미지·상황·계절·무드가 섞인 표현. **바로 상품 검색어로 사용 X.** 먼저 패션 의도로 분해해야 한다.

### 분해 예시

```
"여름철 남친룩"
  → 성별: 남성
  → 계절: 여름
  → 무드: 깔끔함, 데일리, 호감형, 캐주얼
  → 상황: 데이트, 주말 외출, 대학생/직장인 일상
  → 예상 아이템: 린넨 셔츠, 반팔 니트, 와이드 슬랙스, 연청 데님, 버뮤다 팬츠, 미니멀 스니커즈, 샌들
  → 예상 색상: 화이트, 스카이블루, 네이비, 베이지, 그레이
```

### enum 화이트리스트 검증 (파싱 결과 정합)

프롬프트 의도 파싱(LLM + JSON schema) 결과를 **그대로 신뢰하지 않고** 한국어 패션 taxonomy enum 화이트리스트로 검증한다.

- 분해 결과의 {계절·무드·상황·아이템·색상·핏·소재·카테고리} 값을 §1 표준 enum(`products` 태그와 동일 화이트리스트)에 대조한다.
- 화이트리스트에 없는 값(LLM hallucination·오타·자유 입력)은 버리거나 가장 가까운 enum으로 정규화한 뒤에만 B-path 검색·A-path 생성에 투입한다.
- §1의 상품 태그 enum 검증과 **같은 화이트리스트**를 공유해, 프롬프트 측과 상품 측 어휘가 어긋나지 않게 한다(매칭 정확도 보장).
- 이 화이트리스트의 **실제 값 목록 = 부록 A (한국어 패션 taxonomy enum, V0 초안)** — `situation`·`mood`·`color`·`fit` 4개 차원. `category`·`season`은 §1의 닫힌 enum이다.

### 외부 trend data 활용

| 소스 | 용도 |
|---|---|
| 네이버 데이터랩 | 한국어 검색 트렌드·시즌성 |
| Google Trends | 국내/글로벌 관심도 비교 |
| YouTube 검색 결과 | 룩북·하울·코디 추천 영상에서 아이템 조합 추출 |
| Pinterest Trends | 무드보드·시각 스타일 패턴 |
| 네이버/구글 검색 결과 | 블로그·매거진 반복 등장 표현 |
| I.F 내부 데이터 | 클릭/저장/구매링크 클릭 (시간 지나면 가장 신뢰도 높음) |

### 주의

- 외부 trend는 **상대적 관심도**·**시즌성** 파악용. 절대값 X
- 플랫폼마다 사용자 성향 다름 — 하나에 의존 금지
- "남친룩" 등 표현은 시대·계절에 따라 의미 변동 — **주기적 갱신**
- trend data를 그대로 복제 X. 반복 등장하는 아이템·색상·핏·무드·상황 맥락만 추출
- 최종 추천은 항상 실제 구매 가능한 상품과 연결되어야 함

## §7. Fine-Tuning은 첫 단계가 아님

초기부터 이미지 생성 모델을 직접 학습/파인튜닝하는 것은 권장하지 않는다.

### 먼저 해야 할 일

1. 좋은 상품 데이터셋 만들기 (§1)
2. 상품 이미지 캡션 만들기 (§2)
3. 스타일 태그 체계 만들기 (§1)
4. 프롬프트 템플릿 만들기 (§3)
5. 생성 결과와 실제 상품 매칭 정확도 평가하기 (§5)

### 충분한 데이터가 쌓인 후

V1 이상에서 다음 검토 가능:
- LoRA (스타일별 어댑터)
- DreamBooth (특정 룩 재현)
- ControlNet (포즈·구도 제어)
- IP-Adapter (참조 이미지 기반)
- fashion-specific embedding

**초기에는 "모델을 학습시키는 것"보다 "모델이 이해하기 좋은 데이터·프롬프트 구조를 만드는 것"이 우선.**

## §8. 개발 우선순위 (1 → 12)

V0 부트스트랩부터 V1+까지 순서대로:

| 순서 | 작업 | V0/V0.5/V1 |
|---|---|---|
| 1 | 상품 데이터 스키마 정의 | V0 (docs/DATA_MODEL.md 완료) |
| 2 | 초기 상품 데이터 수집 | V0 — 사용자분 큐레이션 50→500개 |
| 3 | 상품 이미지 캡셔닝 | V0 — AI 자동 + 사람 검수 |
| 4 | 스타일/무드/상황 taxonomy 설계 | V0 — enum 화이트리스트 |
| 5 | 역프롬프트 생성 | V0 — curated look 구축 시 |
| 6 | 한국어 상황형 프롬프트 → taxonomy 매핑 | V0 — `/api/prompts/interpret`의 핵심 |
| 7 | 외부 trend data 기반 시즌별 스타일 사전 | V0 — 시즌 데모 프롬프트(Explore 피드 구성) |
| 8 | 텍스트/이미지 임베딩 저장 | **V0.5** (V0는 태그·캡션 기반 검색으로 시작) |
| 9 | 프롬프트 기반 상품 검색 | V0 — B-path (curated 검색) |
| 10 | AI 생성 이미지 기반 상품 검색 | V0.5 (A-path 정확도 향상) |
| 11 | 사용자 피드백 기반 매칭 개선 | V0.5 — Human eval loop 운영 |
| 12 | 모델 파인튜닝 검토 | V1 이상 |

이 순서를 지키는 이유: I.F의 경쟁력은 **범용 이미지 생성 모델 자체가 아니라 "사용자가 상상한 스타일을 실제 구매 가능한 국내 패션 상품으로 얼마나 잘 번역하는가"**에 있기 때문.

### B-path / A-path 운영 메모

- **B-path (curated 검색, 약 90%)** — §4 가중합 점수 ≥ 0.70 시 적중. 미달이면 A-path로 fallback.
- **A-path (실시간 AI 생성, fallback)** — **OpenAI GPT Image 2 · Medium · 1024×1024 고정**($0.053 ≈ 74원/이미지). 모델·quality·해상도는 운영 기준으로 고정이며 변경은 ADR-003에서만 다룬다. → `docs/ADR.md` ADR-003 참조.

### 생성 이미지 영속화

A-path로 생성한 룩 이미지는 **생성 즉시 Supabase Storage에 저장**하고, `docs/DATA_MODEL.md` `looks.generated_image_url`에는 OpenAI URL이 아니라 Storage 경로(서명 URL)를 보관한다 — OpenAI 임시 URL은 24시간 후 만료되므로 그대로 두면 저장·공유 시점에 깨진다.

## I.F의 핵심 데이터 자산

```
- 상품 이미지
- 상품 캡션
- 상품 속성 태그
- 상품별 역프롬프트

- 사용자 입력 프롬프트
- 생성된 룩 이미지

- 클릭/저장/구매 전환 데이터
```

이 데이터가 쌓이면 I.F는 단순 AI 패션 이미지 생성 서비스가 아니라 **한국 여성 패션에 특화된 프롬프트-상품 연결 엔진**으로 발전할 수 있다.

## §9. 데이터 수집 SOP (운영 방식)

§8 우선순위 2·3번(초기 상품 데이터 수집 → 캡셔닝)의 **운영 방식**을 정의한다. `개발_전_진행_체크리스트.md` §6 "500개 curated look DB 운영 방식 정리(수집·검수·태깅·공개/비공개·상품 링크 관리)"에 대응한다. 이 SOP는 **설계·룰**이며, 실제 50→500 수집과 매칭 검증은 앱 부트스트랩 + DB 마이그레이션 이후에 같은 룰로 실행한다.

### 9-0. 소싱 워크플로우

- **분담**: 사람(PO/운영자) = 소싱·최종검수, AI = 구조화·초안. PO가 29CM·무신사·브랜드 자사몰에서 룩 컨셉에 맞는 실제 판매 상품을 **직접 고르고** URL·상품명·가격을 입력하면, AI가 enum 태깅·캡션·역프롬프트 초안을 생성하고 PO가 검수·확정한다.
- **자동 크롤링 금지**: "전체 쇼핑몰 자동 크롤링"은 V0 Non-Goal(CLAUDE.md, `docs/PRD.md`). 사람이 고른 것을 AI가 구조화하는 것이지 자동 수집이 아니다.
- **`source_platform`**: '29CM' · 'MUSINSA' · '브랜드자사몰' 3종 enum과 정확히 일치(다른 값 추가는 스키마 변경 사안).

### 9-1. 상품 이미지 정책 (저작권·ToS)

- `image_url`에는 **외부 몰 CDN URL을 그대로** 두고, 상품 카드는 외부 `product_url`로 이동시킨다. **사본 저장·핫링킹 사본 금지**(무단 복제 저작권 리스크 회피).
- 한계: 몰이 referer를 차단하거나 이미지를 교체·삭제하면 끊길 수 있다 → 부트스트랩 후 제휴/파트너 자산·캐싱 정책으로 재검토.
- `docs/DATA_MODEL.md` §15.3 `image_url`은 NOT NULL만 규정하고 출처를 강제하지 않으므로, 출처 정책은 이 SOP가 정본.

### 9-2. 태깅 룰 — "Session 4 안정 화이트리스트"

부록 A taxonomy(317개)는 아직 `.ts` 미전환이고 펜딩 정제(situation 저빈도 컷, fit 비핏 항목 `proportion_hint` 분리, color 경계 hex 가이드)로 key가 바뀔 수 있다. **펜딩 영향이 없는 안정 부분집합으로만 태깅**해 재작업 리스크를 0으로 만든다.

- **허용 (고정 key ★, §1 보존)**
  - situation — `date` · `work` · `travel` · `sport` · `wedding_guest` · `picnic`
  - mood — `casual` · `lovely` · `minimal` · `street` · `ballet_core` · `old_money`
  - color — `navy` · `ivory` · `light_blue`
  - fit — `over` · `slim` · `hip_cover` · `semi_wide` · `high_waist`
- **허용 (이미 닫힌 enum)**: category `top/bottom/dress/outer` · season `spring/summer/fall/winter`
- **금지·보류**: fit 비핏 항목(`tummy_cover` · `leg_lengthening` · `wide_bottom` 등 — proportion_hint 분리 검토 중), situation 저빈도 컷 후보(`climbing` · `cycling` · 수영복 제외 겉옷군), color 경계 톤(`taupe` · `brick` · `terracotta` — hex 미확정)
- 수집 시작 후 PO와 화이트리스트를 점진 확장하고, Phase 4 `.ts` 전환 시 전체 정합한다.

### 9-3. 캡션 룰

- 상품당 2종을 모두 작성: `caption_simple`(객관 속성) + `caption_searchable`(상황+무드+색+핏 합성). 예시·형식은 §2.
- AI 자동 초안 + PO 스팟체크(잘못된 색/소재/핏 인식 수정).
- **저장**: V0에선 `data/curated/products.csv` 템플릿에 선수집. 실제 `products` 컬럼 확정은 부트스트랩 `002`에서(§2 저장 위치 · `docs/DATA_MODEL.md` §15.3 메모).

### 9-4. 역프롬프트 룰

- 검색 매칭용 역프롬프트(사용자가 칠 법한 표현 — "벚꽃 데이트룩" · "여리여리" · "하체커버")는 **`looks`의 태그 배열(`situation_tags`/`mood_tags`/`color_tags`/`fit_tags`)과 `base_prompt`로 흡수**한다. 신규 컬럼은 만들지 않는다(10테이블/컬럼 freeze 존중, §3).
- 이미지 생성용 역프롬프트는 룩 이미지 생성 시 사용(부트스트랩 후, A-path/OpenAI).

### 9-5. curated-look 빌드 절차 (1건 end-to-end)

1. **컨셉** — 한국 20-30대 여성 데일리. `looks.title` + `base_prompt` 초안.
2. **룩 이미지** — 전신 착장(상의+하의 또는 원피스+아우터) 가시. 상반신 클로즈업·하의 잘림·런웨이/코스튬은 FAIL → 재생성. (실제 생성은 부트스트랩 후 A-path.)
3. **이미지 영속화** — Storage 경로만 저장, OpenAI 24h URL 저장 금지("생성 이미지 영속화" · `docs/DATA_MODEL.md` §15.2). 사전 단계에선 placeholder `pending_storage:looks/<id>.png`.
4. **역프롬프트**(9-4) — 태그·`base_prompt`로 흡수.
5. **태깅**(9-2) — 안정 화이트리스트 안에서.
6. **상품 3-5개 큐레이션**(9-0) — NOT NULL: `product_name` · `product_url` · `image_url` · `category`.
7. **캡션 2종**(9-3).
8. **look_products 매핑** — `item_role`(main_top/main_bottom/main_outer/similar/related) · `recommendation_type`(main_combo/similar/related) · `sort_order`. **UNIQUE(look_id, product_id, item_role) 준수.**
9. **QA 게이트** — 9-6 체크리스트 통과해야 룩 "확정".

### 9-6. 스키마 정합 수집 템플릿 + QA

앱·DB 부트스트랩 전이라 수집물은 **frozen 스키마에 1:1 정합되는 중간 템플릿(CSV)**으로 모으고, 부트스트랩 후 시드 스크립트로 주입한다. 템플릿·매핑·QA 체크리스트는 `data/` 운영 자산으로 제공한다:

- `data/schema/{products,looks,look_products}.columns.md` — CSV 헤더 ↔ `docs/DATA_MODEL.md` §15.2~15.4 컬럼 매핑. 배열 컬럼은 **파이프 구분**(`casual|minimal`), 조인은 로컬 ID(`look_local_id`/`product_local_id`, 시드 시 uuid 부여).
- `data/curated/*.csv` — 헤더만 있는 빈 템플릿(PO가 Sheets/Excel로 채움).
- `data/QA_CHECKLIST.md` — 룩 1건당 통과 게이트.

**QA 게이트(룩 1건)**: ① NOT NULL 누락 0 ② 태그가 안정 화이트리스트 안(위반 0) ③ 룩 이미지 품질 기준 통과 ④ 상품 3-5개 + 캡션 2종 존재 ⑤ look_products UNIQUE 위반 0 ⑥ 상품 이미지 사본 저장 0.

### 9-7. 설명용 예시 (가상 1건 — 데이터 행 아님)

| 필드 | 값 |
|---|---|
| `looks.title` | 벚꽃 데이트 여리여리 룩 |
| `looks.base_prompt` | 봄 벚꽃 배경, 여리여리한 무드의 데이트룩. 아이보리 니트 가디건 + 라이트블루 플레어 스커트 |

### 9-8. 범위 메모

이 SOP는 **운영 방식 설계**까지다. 실제 룩·상품 수집(파일럿 50 → 500), 룩 이미지 생성, B-path 매칭(≥0.70) 검증은 앱 부트스트랩 + DB 마이그레이션(`002_init_looks_products.sql`) 이후 같은 룰로 실행한다.

## 부록 A. 한국어 패션 taxonomy enum (V0 초안)

§6의 "enum 화이트리스트 검증"이 대조하는 **실제 값 목록**이다. 상품 태그(`products`, §1)와 프롬프트 의도 파싱(`/api/prompts/interpret`) 양쪽이 **같은 화이트리스트**를 공유한다 — 그래야 프롬프트 어휘와 상품 어휘가 어긋나지 않는다(§6).

- **범위**: 자유 어휘가 큰 4개 차원 — `situation`·`mood`·`color`·`fit`. 나머지는 이미 닫힌 enum이다 — `category`(top/bottom/dress/outer 4종, §1)·`season`(spring/summer/fall/winter 4종). `material`·`subcategory`는 별도 차원으로 추후 작성한다.
- **상태**: V0 초안. **아직 `.ts`로 옮기지 않는다** — Phase 4(taxonomy 설계, §8 4번) 진입 직전에 아래 "정제·운영 메모"를 반영해 `.ts` enum으로 변환한다. 기준은 한국 20-30대 여성 데일리 패션이며 런웨이·코스튬·과한 컨셉·남성 전용·아동·신발/가방/액세서리는 제외한다.

### 정제·운영 메모 (Phase 4 `.ts` 전환 전)

본 초안은 "누락보다 과수집" 원칙으로 망라적으로 담았다(빈도 데이터로 컷하는 게 누락을 채우는 것보다 쉽다). `.ts` enum 확정 전 다음을 정리한다.

- **교차차원 직교성 (적용 완료)**: 무드에 섞여 있던 상황 미러(`*_look`)·`tennis_core`는 제거하고 situation으로 일원화했다(한국어 별칭은 이미 situation에 보존됨). 꾸안꾸는 mood(`kkuankku`) 한 곳으로, 하객은 situation(`wedding_guest`) 한 곳으로 통일했다. `여리여리`는 mood(`yeori_yeori`, 분위기)와 fit(`wispy`, 실루엣)으로 의미를 분리해 동일 key 문자열 충돌을 제거했다.
- **`wedding_guest` 정규화 (PO 결정, 적용 완료)**: 하객 key는 본래 `gehakdaeng`이었으나 "하객"의 표준 로마자와 어긋나는 표기여서, PO 결정(2026-06-02)으로 `wedding_guest`로 정규화했다 — §1·부록 A·거울 §9.9 동시 갱신. 정장형 변형은 `wedding_guest_formal`.
- **situation 상한 근접(94개)**: 50~100 범위 내이나 상한에 가깝다. `climbing`·`cycling`·`coming_of_age`·`market_flea`, 그리고 수영복 제외 겉옷군(`beach`·`water_park`·`swimming`)은 V0 4카테고리(top/bottom/dress/outer) 상품 매칭이 빈약할 수 있어 V1 사용 로그로 통합·컷을 재검토한다.
- **fit 비(非)핏 항목 분리 후보**: 코디 조합 힌트(`loose_top`·`fitted_top`·`wide_bottom`·`slim_bottom`·`loose_fit_overall`·`fitted_overall`·`balanced_proportion`)와 체형 보완 효과(`tummy_cover`·`leg_lengthening`·`slim_look`)는 `products.fit` 단일값에 부적합하다 — 프롬프트 파싱 전용 또는 별도 필드(`proportion_hint`)로 분리할지 검토한다. (`hip_cover`는 고정 key라 유지.)
- **color 태깅 가이드**: 그레이지·뉴트럴 경계(`taupe`·`warm_gray`·`stone_gray`·`khaki_beige`)와 흙빛 적/오렌지(`brick`·`terracotta`·`rust`)는 텍스트 설명만으로 분별이 어렵다 — 상품 태깅 가이드에 대표 hex 샘플을 붙인다. `multicolor`는 단일 색 원칙의 예외(escape hatch, 진짜 다색일 때만). `gold`·`silver`의 강한 메탈릭 광택 차단은 색상값이 아니라 material/finish 또는 생성 가드에서 통제한다.
- **LLM 정규화 우선순위**: 인접 항목(`work`/`office_business`/`office_casual`, chic 계열 등)은 사용자 입력이 모호할 때 어느 enum으로 정규화할지 `/api/prompts/interpret` 프롬프트에 우선순위를 명시한다(§6).
